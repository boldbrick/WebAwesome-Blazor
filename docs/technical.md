# WebAwesome.Blazor Technical Standards

The engineering standards and practices for authoring and maintaining the Web Awesome Blazor wrappers. This is the durable wrapper authoring contract; general C# style lives in `CLAUDE.md`, the upgrade pipeline and testing strategy in `docs\UPGRADE-PROCESS.md`, and contribution process in `CONTRIBUTING.md`. Task-specific plans and evaluations that shaped these standards are archived under `tasks\<epic>\<task>\`.

## Architecture principles

- **Pure C# render trees.** Wrappers are `ComponentBase` descendants implementing `BuildRenderTree` by hand — no `.razor` markup. This keeps attribute emission, event wiring, and sequence numbering under explicit control.
- **Web Awesome components are self-contained.** The upstream web components handle their own initialization, internal state, DOM manipulation, and third-party library integrations. A wrapper renders the correct tag with the correct attributes, slots, and event subscriptions — nothing more. Never re-implement behavior the custom element already provides.
- **Naming**: tag `wa-foo-bar` → class `WaFooBar`, one class per file in `src\WebAwesome.Blazor\Components\`. Web Awesome's CSS-only layout utilities (no `wa-*` element, just markup + classes) are wrapped as components too, in `src\WebAwesome.Blazor\Layouts\`. Shared infrastructure lives in `src\WebAwesome.Blazor\Base\`.
- **Completeness**: every documented attribute, event, slot, and method of the bound Web Awesome version has a wrapper counterpart (mechanically enforced — see the parity suite in `docs\UPGRADE-PROCESS.md`). Intentional deviations are recorded in `parity-config.json` with a reason, never silently.
- **Every element wrapper** exposes `[Parameter(CaptureUnmatchedValues = true)] AdditionalAttributes` pass-through and captures `ElementReference? Element`.

## Render tree discipline

- **Constant sequence numbers, never `sequence++`.** Incrementing sequence numbers defeats Blazor's diffing and produces false-positive DOM changes. Number statically with gaps between sections (attributes, events, element ref, slots); gaps are fine. When a helper method builds a portion, pass it a constant base and number `sequence + 0`, `sequence + 1`, … inside.
- **Conditional emission via the shared extensions** (`Base\RenderTreeBuilderExtensions.cs`): `AddAttributeIfNotNullOrEmpty` / `AddAttributeIfNotNull` for attributes, `AddAttributeIfHasDelegate` for events. Booleans never go through `ToString()` (`AddAttributeIfNotNull` rejects them at compile time): a plain `bool` uses `builder.AddAttribute` (present or absent); a `bool?` for a Lit `type: Boolean` attribute uses `AddBooleanAttribute`; a `bool?` for an attribute with a `"true"`/`"false"` converter (check the component source, e.g. `spellcheck`) uses `AddTrueFalseAttribute`, which is also the only way to turn off an attribute whose Web Awesome default is true. Inline `if (X.HasDelegate)` guards are reserved for cases where the emitted callback differs from the guarded one (factory-wrapped handlers) or sequence numbers increment conditionally.
- **Numbers render in the invariant culture.** Blazor formats a non-string attribute value with the current culture, so `builder.AddAttribute(n, "distance", Distance)` renders `"0,5"` under cs-CZ, which Web Awesome can't parse. Pass a number through `AddNumberAttribute` (non-nullable; nothing while it holds the element default, see the sticky rule below) or `AddAttributeIfNotNull` (nullable); both format invariantly. Parse element values with `ChangeEventArgsExtensions.TryParseJsNumber`, and override `FormatValueAsString` with the invariant culture in a numeric `InputBase` wrapper. `RenderedAttributeParityTests` renders every wrapper under a hostile culture and fails on a culture-formatted value.
- **Dates and times render in Web Awesome's wire formats, never through `ToString()`.** The invariant default forms (`01/02/2026`, `13:04`) are not what the element parses, so `AddAttributeIfNotNull` and `AddNumberAttribute` reject `DateOnly`, `TimeOnly`, `DateTime` and `DateTimeOffset` at compile time (`CS0619`) and `FormatInvariant` throws for them. Use the dedicated helpers, backed by `Base\WaWireFormat` (which mirrors the element's parsers; re-verify it against the target version's `date-picker/internal/iso.ts`, `matchers.ts` and `time-input/internal/segments.ts`, and the day slot name against the date picker's `renderDay`, on every upgrade): `AddDateAttribute` (ISO `yyyy-MM-dd`), `AddTimeAttribute` (a bound: `HH:mm`, or `HH:mm:ss` with seconds), `AddDateSetAttribute` (ascending ISO dates, space-separated), `AddDaysOfWeekAttribute` (`sun`..`sat`, Sunday first) and `AddDateTimeOffsetAttribute` (`yyyy-MM-ddTHH:mm:ss.fff+hh:mm`, the ECMAScript form `new Date()` reads as one instant). A typed `InputBase` wrapper must override **both** `FormatValueAsString` (the base uses the culture-sensitive `ToString()`) and `TryParseValueFromString`: format exactly as the element emits (a time follows the step rule), parse strictly (`""` binds `null`), and report a failure with a `Constants.*ValidationMessageFormat` through `FormatValidationMessage`. `RenderedAttributeParityTests` (h) checks every sampled date, time, instant, range and set attribute against Web Awesome's own patterns (`WaWirePatterns`).
- **An unset parameter emits no attribute**, so the Web Awesome default applies — wrappers never bake upstream defaults into C#, and a non-nullable parameter holding the element default renders nothing either.
- **Sticky attributes: a rendered attribute is never removed again.** When Blazor removes an attribute, Lit's converter sets the element property to null, not back to its default (a `wa-slider` whose max returns from 50 to the default 100 would get `max = null`, which its arithmetic reads as 0; a tooltip's distance null instead of 8). So every attribute of the wrapper's element goes through the per-component `Base\WaAttributeMemory`: open the element with `var attributes = builder.OpenWaElement(this, 0, "wa-x");` and pass `attributes` to the sticky overload of each helper (`AddAttributeIfNotNull`, `AddAttributeIfNotNullOrEmpty`, `AddNumberAttribute` and `AddDefaultedAttribute` for non-nullable parameters, and the typed helpers); base-class helpers use `WaAttributeMemory.Of(this)`. The memory renders nothing while the parameter is unset (nullable) or has never differed from the element default (non-nullable), and once the attribute has been rendered, a return to null or to the default renders the element default explicitly, from `Base\WaElementDefaults` (the CEM literal defaults, generated by `ElementDefaultsTableTests`, which fails when the file differs from the surface and writes the file to copy over it). Exempt: plain booleans (a removed Lit boolean reads false, its default; a `"true"`/`"false"` converter attribute defaulting to true, `spellcheck`, is in the table and so sticky), attributes whose CEM default is none or computed (`new Date()`), where removal restores the unset state, and attributes of child elements. Never guard an attribute by hand with `if (X != default)`. `RenderedAttributeParityTests` (i) re-renders every parameter back to its default on the same instance and requires the element default; `sticky-attributes.spec.js` proves it on the element properties.
- **Editable values use explicit bindings** in the pattern of Blazor's built-in inputs: emit `value`, an `onchange` handler created with `EventCallback.Factory.CreateBinder`, and call `builder.SetUpdatesAttributeName("value")`. This is mandatory — Blazor's change binder special-cases native `INPUT`/`SELECT` elements only (e.g. it reads `.checked` solely for native checkboxes), so custom elements get no two-way binding for free.

## Public API conventions

The public API is C# — it must feel idiomatic to .NET consumers, not mirror DOM attribute spellings or JavaScript typing:

- **Natural PascalCase word splits**, not mechanical kebab-case conversion: `MaxLength` (not `Maxlength`), `SrcDoc`, `AllowFullScreen`, `AutoFocus`, `InputMode`. Each such rename is recorded in `parity-config.json` `attributeOverrides`.
- **Strong typing throughout.** Closed value sets become nullable C# enums in `Components\Enums.cs` (or `Layouts\Enums.cs`) with a `ToHtmlValue()` switch-expression extension: a union of string or number literals (`'a' | 'b'`, `1 | 2`, alias-resolved; `EnumValueParityTests.NoStringOrDecimalParameter_IsBoundToLiteralUnion` fails on a `string` or `decimal` parameter bound to one, allowlist `untypedLiteralUnionAttributes`), and a plain `string` the element reads as a closed token set (`sandbox`, `referrerpolicy`, `heading-level`), a `[Flags]` enum for a token list, recorded in `tokenListAttributes`. Existing enums (`WaSize`, `WaVariant`, `WaPlacement`, …) are reused whenever the value set matches, never duplicated. An enum that travels as JSON (event args, the data grid column model) carries a `[JsonConverter]` derived from `Base\WaEnumJsonConverter`, which writes and reads exactly its `ToHtmlValue()` strings and fails on an unknown one; a payload the JS initializer projects to a known shape is a record (`WaMutationRecord`, `WaResizeEntry`/`WaRect`, `WaElementInfo`), never `object[]`. A `number | 'any'` step is `WaStep?` (a positive number or `WaStep.Any`, implicit from the numeric literals Razor produces, invariant `ToString()`); an attribute read by an `"on"`/`"off"` converter (`autocorrect`) is `bool?` rendered by `AddOnOffAttribute` and listed in `onOffAttributes`. A list attribute is `IReadOnlyList<double>?`, `IReadOnlyList<string>?`, `IReadOnlySet<string>?` (ordinal order) or `IReadOnlyList<TEnum>?`, joined with exactly the separator the element splits it on (`AddNumberListAttribute`, `AddTokenListAttribute`, `AddTokenSetAttribute`; an item that would split, or a non-finite number, throws); cite the separator in `WaWirePatterns.ListSeparators`, which (h) reads the rendered list with. Where Web Awesome uses a string only for lack of a JS type, the parameter takes the .NET type and the wrapper converts it: a date is `DateOnly?`, a time of day `TimeOnly?`, an instant `DateTimeOffset?` (rendered with its offset; never `DateTime`, whose unspecified kind the browser would read as local time), a date range `WaDateRange?`, a set of dates or weekdays `IReadOnlySet<DateOnly>?`/`IReadOnlySet<DayOfWeek>?`. A null or empty collection renders no attribute. A string stays a string only where the value set is open (URLs, CSS lengths, BCP 47 locales, IANA time zones, colours).
- **A mode that changes the value's type is a wrapper of its own**, not a parameter: `WaDateInput`/`WaDatePicker` bind `DateOnly?`, `WaDateRangeInput`/`WaDateRangePicker` bind `WaDateRange?` and always render `mode="range"`, sharing their element's base class (the precedent is `WaRange` next to `WaSlider`).
- **Numbers**: properties measured in pixels or milliseconds are `int?`; `double?` only where fractional values are meaningful (e.g. animation iteration start).
- **Defaults are the element's.** A parameter's C# default is Web Awesome's default for the attribute (the CEM `default`): an optional parameter is nullable, defaults to `null` and renders nothing when unset, so the element's own default (including a localized label, or a variant inherited from an enclosing element) applies; a parameter that must be non-nullable carries exactly Web Awesome's default, declared as a named public constant `Default<Name>` on the wrapper (`WaCopyButton.DefaultFeedbackDuration`, `WaSlider.DefaultMax`) and used as its initializer, and renders nothing while it holds it (durations stay `int` milliseconds). Never choose a "nicer" default, and never skip rendering a value because it equals a C# default that differs from the element's, which makes that value unreachable (`WaDropdown.Distance = 8` rendered nothing, so an explicit 8 gave 0). `RenderedAttributeParityTests.BaselineRender_EmitsOnlyElementDefaults` (no CEM attribute renders unset, not even at its default, and a non-nullable parameter set to its default on the first render renders nothing) and `ParameterDefaults_MatchTheElementDefaults` (the C# value consumers see, and its `Default<Name>` constant) enforce it; a default the CEM cannot express goes into `divergentParameterDefaults`, a structural reason to render one into `wrapperDefaultAttributes`, each with a reason.
- **Events**: `wa-x` → `[Parameter] EventCallback<TArgs> OnX`, with typed event args classes in `Components\EventArgs.cs` when the event carries a `detail`. Event args classes inherit `System.EventArgs` (the runtime rejects them at dispatch otherwise).
- **Element methods**: documented instance methods become `XxxAsync()` wrapper methods.
- **The public API snapshot is a change detector, not correctness coverage.** `PublicApiSnapshotTests` only proves the surface didn't change unnoticed; a promoted baseline says nothing about whether a member works (it enshrined every dead callback before 3.12.0). Correctness comes from the render-based parity checks and the browser specs.
- **Slots**: named slots → `RenderFragment` parameters (`XxxContent`), the default slot → `ChildContent`. Every slot the element declares gets one, and a wrapper renders content only into slots its element declares; `SlotParityTests` checks both directions on the rendered markup (a slot that genuinely cannot be a parameter goes into `unreachableSlots` with a reason). Wrap the fragment in an element carrying the `slot` attribute (a `span`, or a `div` for block content); where the slot lays out each slotted element as an item of its own (`wa-slider`'s `reference` labels), give that wrapper `style="display: contents"` (`Constants.TransparentSlotWrapperStyle`) so the fragment's elements become the items. A family of slots named after data (`day-YYYY-MM-DD`) is a host/sub-component pair instead, see "Dynamic slots".

## Event delivery contract

Binding a Web Awesome custom event requires two coordinated pieces; missing either fails silently (no build error, no runtime error, the event just never fires):

1. In the render tree, the event is bound under the **`on`-prefixed attribute name**: `builder.AddAttributeIfHasDelegate(seq, "onwa-show", OnShow)`.
2. The event name is **registered with `Blazor.registerCustomEventType`** in the JS initializer `src\WebAwesome.Blazor\wwwroot\WebAwesome.Blazor.lib.module.js` — in the plain `eventNames` list when the event's `detail` is JSON-safe and maps 1:1 onto the typed args, or with a `specialArgs` mapping when the detail carries DOM nodes or the typed args need derived values (payload shapes must stay in sync with `Components\EventArgs.cs`; deserialization is case-insensitive and ignores extra properties).

Only bind events the bound Web Awesome version actually emits (check the CEM and the component's `@event` JSDoc), and bind each `EventCallback` to the event its name stands for: `wa-after-hide` → `OnAfterHide`, `blur` → `OnBlur`, with deviations in `parity-config.json` `eventOverrides`. Native DOM events the CEM doesn't list (`click`, `focus`, `blur`, the keyboard events) are admitted through `nativeDomEvents`. A callback the wrapper raises from another handler (e.g. `OnCheckedChange` from the value binding's `change`) goes into `derivedEventCallbacks`. Number-valued elements bind the `onnumericchange`/`onnumericinput` aliases (`Constants.*EventAttribute`) instead of `onchange`/`oninput`.

**Where Blazor listens.** Blazor delivers a custom event (and a bubbling built-in such as `keydown`) only as it bubbles to the document, and a non-bubbling built-in (`focus`, `blur`) only to `composedPath()[0]`, the innermost element. An event that never gets there is dropped silently, even with a correct binding and registration:

- **Focus**: bind `OnFocus`/`OnBlur` to the bubbling, composed `onfocusin`/`onfocusout` wherever the focus can land inside the shadow root (every `WaInputBase` control, `WaButton`, `WaFileInput`); `FocusEventArgs.Type` is then `"focusin"`/`"focusout"`. A focus move between two parts of the same shadow root (OTP segments, the thumbs of a range slider) is not dispatched outside it, so it raises nothing; a move between the control and content slotted into it (one radio of a group to the next, a select's input into its option list) raises `OnBlur` then `OnFocus`, which the callback docs state. Keep `onfocus`/`onblur` only where the host itself takes the focus (`WaRadio`, `WaTab`, `WaDropdownItem`): there `focusin` would also arrive from nested items (submenus). The checks treat `focusin`/`focusout` as the element's `focus`/`blur` through `bubblingEventAliases`.
- **Non-bubbling or stopped events**: an element event that does not bubble (`wa-color-picker`'s popup events, `wa-intersect`) or whose propagation the element stops in its shadow root (`keydown` in `wa-select`, `wa-combobox`, `wa-color-picker`) is **relayed** by the JS initializer. Add an entry to its `relayedEvents` map (private Blazor name → `{ event, hosts, source }`, `source: 'host'` when only the host's own dispatch counts, `'subtree'` for native events from inside it), a `Constants.Relayed*EventAttribute` with the `on`-prefixed private name, and bind it with `AddRelayedEventIfHasDelegate`, never `AddAttributeIfHasDelegate`: the relayed event bubbles, and the helper adds Blazor's `stopPropagation` so it reaches no other wrapper of the same element further up. A capture-phase listener on the document re-dispatches each original event once, as a bubbling, composed `CustomEvent` under the private name on its host; the payload is the original event's (`specialArgs`, the sanitized detail, or Blazor's keyboard shape), and the original is left untouched, so page listeners never see a second `wa-*` event. A `WaInputBase` wrapper relays its keydown by overriding `RelaysKeyDown` and calling `AddRelayedKeyDownHandler`. Each upgrade, check the component sources for `bubbles: false`, plain `new CustomEvent(` dispatches and `stopPropagation()` in keyboard handlers.

Two test classes enforce the contract on the **rendered** output, not the source text: `RenderedWrapperCatalog` renders every wrapper with bUnit, once per `EventCallback` with a no-op delegate, and reads the handler names (and Blazor `stopPropagation` directives) on the root element from the render tree. `EventCallbackBindingParityTests` compares them with the CEM events of the tag the wrapper renders, resolving aliases, relays and `bubblingEventAliases` to the event they stand for. `EventBindingRegistrationTests` compares them with the JS initializer's registrations, in both directions: a relayed name must be private, have its constant, be bound only on its hosts and always with `stopPropagation`. Neither can see whether an event reaches Blazor in a real browser; only the e2e dispatch specs prove that, so every callback needs one (`event-coverage.spec.js`).

## Icon slot convenience

Components exposing an icon-shaped slot — a `start`/`end` slot documented as accepting "an element such as `wa-icon`", or a dedicated `*-icon` slot (`expand-icon`, `copy-icon`, …) — get a `<Slot>IconName` string parameter (`StartIconName`, `ExpandIconName`, …) alongside the slot's `RenderFragment`:

- Rendering goes through `RenderTreeBuilderExtensions.AddIconSlot(builder, sequence, slotName, iconName)`, which emits a `wa-icon` with a `name` attribute (and `slot` when not the default) for a non-empty name.
- **Fragment wins**: when the slot has a `RenderFragment` counterpart, the icon parameter renders only while that fragment is `null`; the parameter's doc comment states "Convenience alternative to `<FragmentName>`; ignored when the fragment is set."
- Pane-like `start`/`end` slots holding arbitrary panel content (e.g. split-panel panes) are excluded from this convention.

## Dynamic slots

A slot whose name Web Awesome builds from data, one per value (`wa-date-input`/`wa-date-picker` `day-YYYY-MM-DD`, one per date), cannot be a fixed `RenderFragment` parameter. Expose such a family as a host/sub-component pair, following `WaDayContent`:

- **The sub-component** takes the typed key as `[Parameter, EditorRequired]` (a `DateOnly`, never a string) and its `ChildContent`, and renders `<span slot="…">` around the content, nothing when the content is null. The name is formatted through `WaWireFormat` exactly as the element builds it, culture-free (`FormatDaySlotName`: `day-` and `formatIsoDate`, as the date picker's `renderDay` does).
- **The host** (the element wrapper's base: `WaDateInputBase`, `WaDatePickerBase`) takes a `ChildContent`, documented as being for the sub-component when the element has no default slot, and renders it directly inside the element through a helper (`FormControlRendering.AddDayContent`) that wraps it in a **fixed** (`IsFixed`) `CascadingValue` of a small internal host interface (`IWaDayContentHost`). The cascading value renders no DOM, so each span is a direct child of the element, as a slot assignment requires; being fixed, it adds no re-render subscriptions.
- **Placement is enforced**: without a cascaded host (outside the host, or inside the content of another slot, where the span would not be a direct child), the sub-component throws `InvalidOperationException` naming the hosts.
- **Registration**: the sub-component tells its host when its slot appears, moves to another key or disappears (from `OnParametersSet` and `Dispose`). A host acts on it only where its element needs it. `wa-date-picker` renders the slot in every cell, so the browser assigns content added at any time. `wa-date-input` forwards the day slots to its inner calendar only on its first update and on its default slot's `slotchange`, which a day-slotted child never causes, so `WaDateInputBase` fires that `slotchange` after its next render (`signalDefaultSlotChange` in the interop module: an empty text node appended and removed), rendering itself when the change came from a component that rendered on its own. Prefer such a nudge of the element's own mechanism to reimplementing it, and re-verify the element's forwarding in the source every upgrade (`updateForwardedDaySlots`); `day-content.spec.js` fails when it breaks.
- **Duplicates are not rejected**: every element assigned to one slot name is shown, in document order, so two contents for one key both show; the sub-component's docs say so.
- **JS-only per-cell callbacks** (`dayContent`, `isDateDisabled`) are not wrapped: they would need a JS round-trip per rendered cell. The host's docs point to the sub-component and the typed attributes (`DisabledDates`).
- **Parity**: `SlotParityTests` resolves a rendered name against a patterned CEM slot name (the whole `-`-separated segments `YYYY`, `MM`, `DD` match digits; add a placeholder to `SlotNamePlaceholders` for a new kind of key), samples the host's `ChildContent` as the sub-component holding the probe (`FragmentSample`), and counts a `sourceVerifiedSlots` entry as declared where the CEM omits a slot the source renders (`wa-date-picker`'s day slots; the entry goes stale once a CEM declares it). A new sub-component goes into `RenderedWrapperCatalog.HostedSlotContentComponents`, since it cannot render on its own.

## Form controls

- Form-associated components inherit **`WaInputBase<TValue>`** (itself deriving from Blazor's `InputBase<TValue>`), giving typed values, `@bind-Value`, full `EditForm`/`EditContext` participation, DataAnnotations validation, and validation CSS classes, usually through one of its intermediate bases. Pick the deepest tier whose cluster the element declares **completely** in the CEM:

  | Base (`Base\`) | Derive when the element has | Declares | Render helpers | Wrappers |
  |---|---|---|---|---|
  | `WaInputBase<TValue>` | only a partial label/hint subset | name, class, style, size, disabled, the focus/keyboard/input events, live-value sync, `IFormValidation` | `AddCommonAttributes`, `AddCommonEventHandlers`, `AddLabelAndHintSlots(builder, seq, markupLabel, markupHint)` | `WaCheckbox`, `WaSwitch`, `WaRating`, `WaOtpInput` |
  | `WaLabeledInputBase<TValue>` | the whole label cluster: `label`/`hint` attributes and slots, `with-label`, `with-hint` | `Label`, `Hint`, `MarkupLabel`, `MarkupHint`, `WithLabel`, `WithHint` (`IWaLabeledControl`) | `AddLabelAndHintAttributes(builder, 12)`, `AddWithHintAndLabelAttributes(builder, 14)`, `AddLabelAndHintSlots(builder, seq)` | `WaInput`, `WaTextArea`, `WaNumberInput`, `WaRadioGroup`, `WaKnownDate` |
  | `WaPopupInputBase<TValue>` (under the labeled base) | the label cluster and a popup: `open`, `show()`/`hide()`, `wa-show`/`wa-hide`/`wa-after-show`/`wa-after-hide` | `Open`, `OnShow`, `OnHide`, `OnAfterShow`, `OnAfterHide`, `ShowAsync`, `HideAsync` (`IWaPopupControl`) | `AddPopupEventHandlers(builder, seq)`; override `RelaysPopupEvents` when the element dispatches the events non-bubbling | `WaSelect`, `WaCombobox`, `WaColorPicker`, `WaDateInput`, `WaTimeInput` |
  | `WaSliderBase<TValue>` (under the labeled base) | `wa-slider` (a dedupe base for its two wrappers) | the shared `wa-slider` parameters and methods, and the render tree; the wrapper adds its value attribute and change handlers through `private protected` hooks | none | `WaSlider`, `WaRange` |
  | `WaDateInputBase<TValue>` (under the popup base) | `wa-date-input` (a dedupe base for its two value types) | every `wa-date-input` parameter, slot, event and method, and the render tree; the wrapper adds the value conversion and, through the `private protected AddSelectionModeAttributes` hook, its mode attributes | `FormControlRendering.AddCalendarAttributes` | `WaDateInput`, `WaDateRangeInput` |

  `WaDatePickerBase<TValue>` is the date picker's counterpart. `wa-date-picker` is not form-associated, so it is a `ComponentBase` with a `Value`/`ValueChanged` pair (and the `private protected FormatValue`/`ParseValue` hooks) rather than an `InputBase`; it shares only `IWaCalendarOptions` and its renderer with the date input (`WaDatePicker`, `WaDateRangePicker`).

  A parameter moves up into a base only when the element of **every** wrapper under that base declares it; parameters shared only crosswise stay on the wrappers (the popup's `Placement` type differs per element, so it stays too). `RenderedAttributeParityTests`, `SlotParityTests` and `ParameterDefaults_MatchTheElementDefaults` fail on a parameter moved too far up, and never shadow an inherited parameter with `new`. Concrete wrappers are closed generic types (`WaSelect : WaPopupInputBase<string?>`): `RenderedWrapperCatalog`, which every render-based check uses, skips abstract and open generic types, so an open generic wrapper would drop out of all of them.
- **Sequence numbers of the shared tiers**: 0 is the element; `AddCommonAttributes(builder, 1)` uses 1..6; the element-specific `Readonly`, `Required`, `MinLength`, `MaxLength`, `Autocomplete` follow at 7..11 in that order, declared by each wrapper whose element declares the attribute; the label cluster uses 12..13 (`label`, `hint`) and 14..15 (`with-hint`, `with-label`, emitted where the element's attribute order puts them). Never add an attribute parameter to `WaInputBase` that some element lacks (`RenderedAttributeParityTests` fails on it). A control with a partial label subset declares `Label`/`Hint`/`MarkupHint` itself and passes `null` to `AddLabelAndHintSlots` for a slot its element lacks (`SlotParityTests` fails on content for an undeclared slot).
- **Capability interfaces** (`Base\IWa*.cs`) type-group the clusters that cut across the bases, for consumers and tests; the `[Parameter]` properties stay declared on the class, and the internal static `FormControlRendering` renders each cluster, so a wrapper never repeats that code. Implement an interface whenever the element declares the whole cluster, also on a control that is not an `InputBase` (`WaFileInput`, `WaCheckboxGroup`); `CapabilityInterfaceParityTests` checks both directions against the CEM (popup and affix clusters on form controls only).

  | Interface | Members | Helpers (`FormControlRendering`) |
  |---|---|---|
  | `IWaLabeledControl` | `Label`, `Hint`, `MarkupLabel`, `MarkupHint`, `WithLabel`, `WithHint` | `AddLabelAndHintAttributes`, `AddWithHintAndLabelAttributes`, `AddLabelAndHintSlots` |
  | `IWaPopupControl` | `Open`, the four popup callbacks, `ShowAsync`, `HideAsync` | `AddPopupEventHandlers` (plain or relayed) |
  | `IWaClearableControl` | `WithClear`, `ClearIconContent`, `OnClear` | `AddWithClearAttribute`, `AddClearEventHandler`, `AddClearIconSlot` |
  | `IWaAffixedControl` | `StartContent`, `EndContent` | `AddAffixSlots` (with the wrapper's `StartIconName`/`EndIconName` shortcut, which yields to the fragment) |
  | `IWaCalendarOptions` | the 13 calendar options of `wa-date-input` and `wa-date-picker` (typed: `DateOnly?` bounds, `IReadOnlySet<DateOnly>?` and `IReadOnlySet<DayOfWeek>?` disabled days) | `AddCalendarAttributes` (sequence + 0..12), used by `WaDateInputBase` and `WaDatePickerBase` |
- **Constraint validation**: controls whose element supports `setCustomValidity()` implement the `WebAwesomeFormControl` interface and expose `SetCustomValidityAsync` (routed through the shared interop service), so new form controls gain custom-validity support via the common ancestor without per-component plumbing.

## JavaScript interop

The entire JS surface is deliberately two small files; there are no per-component JS modules, no `document.getElementById` lookups, and no library-generated element ids:

- **`webawesome-interop.js`** — an ES module lazily imported by the `WebAwesomeJSInterop` service (`Base\WebAwesomeJSInterop.cs`). Everything is driven by `ElementReference`: generic `invokeMethod` / `getProperty` / `setProperty`, `setCustomValidity`, `signalDefaultSlotChange` (see "Dynamic slots"), and Web Awesome's module-level helpers (icon library registration, default icon family, kit code). Those helpers are imported from the entry point the page itself loaded (its Web Awesome script tag, or the configured `WebAwesomeOptions` loader URL when there is none): the registry is module state, and another copy or version of Web Awesome would hold a registry no `wa-icon` reads. `InteropModuleContractTests` checks that every invoked identifier is exported. `JSDisconnectedException` is swallowed (returning a default where a value is expected) — circuits legitimately disconnect.
- **`WebAwesome.Blazor.lib.module.js`** — the Blazor JS initializer, auto-loaded by the runtime, whose only jobs are custom-event registration and the relay of events Blazor cannot receive where Web Awesome dispatches them (see the event delivery contract above).

Rules:

- **Interop is a last resort.** Prefer attribute binding; add an `XxxAsync` method only for element methods the CEM documents (or allowlisted in `parity-config.json` `extraElementMethods` with a reason — these allowlisted names are invisible to the CEM diff and must be re-verified against upstream source every upgrade). Never call methods that merely duplicate an attribute (`show()`/`hide()` vs. an `Open` parameter).
- Method wrappers guard a null `Element` (component not yet rendered).
- New .NET JS-interop APIs replace the module only if they can address a DOM element directly; `ElementReference` is not an `IJSObjectReference`, so the module stays (standing verdict: `tasks\WA-3.0\WAB-7\net10-blazor-evaluation.md`).

## Dependencies

All versions live in `src\Directory.Packages.props` (Central Package Management — see `CLAUDE.md`), with two opposing policies:

- **The library ships minimal floors.** NuGet dependency versions are minimums, so every package the library carries into the nupkg (currently `Microsoft.AspNetCore.Components.Web`, `Microsoft.Extensions.Configuration.Abstractions`) stays at the **base release of the target major** (`9.0.0`, `10.0.0`) — a higher floor would force consumers to upgrade their framework packages for no reason. Raise a floor only when the library genuinely needs a later API or fix, and document why at the version entry. A side effect worth keeping: the test suite then validates against the minimum versions consumers can actually resolve.
- **The test harness and tooling track latest stable.** Test-only and build-only packages (test SDK/framework, bUnit, mocking, analyzers, SourceLink, and framework packages referenced only by tests or the demo apps) are kept current — there is no consumer impact, and staying recent picks up runner fixes and security patches. Known-vulnerability warnings (NU1902) are fixed by lifting the affected package, never by suppressing the warning.

## Multi-targeting

The library targets `net9.0;net10.0` with **a single shared code path — no `#if` divergence in library code**. Multi-targeting exists for dependency hygiene (framework package references conditioned per TFM via Central Package Management), not API divergence; net10.0 (LTS) is the primary, fully tested target. `#if` conditional compilation requires a documented reason; the standing evaluation of why none is warranted is archived at `tasks\WA-3.0\WAB-7\net10-blazor-evaluation.md` and is re-evaluated per .NET release (async validation in .NET 11 is the known future interaction point).

**The one owner-approved exception: attributes typed as a union of value types.** `wa-input`'s `min`/`max` are `number | string` in the CEM (a number for `type="number"`, an ISO date, time or local date-time for the date and time types), which C# before 15 cannot type as one parameter. Until then `WaInput` exposes a raw `string?` `Min`/`Max` plus one strongly typed accessor per value type (`MinDecimal`, `MinLong`, `MinULong`, `MinDate`, `MinTime`, `MinDateTime`, and the same for `Max`), each converted culture-free into the native form; at most one per bound may be set (`OnParametersSet` throws `InvalidOperationException` naming them), and `additionalAttributeParameters` lets the render checks sample each accessor against its attribute. The whole set is wrapped in `#if NET11_0_OR_GREATER` / `#error Use a union type here` / `#else` ... `#endif`, so the net11.0 target cannot build until it is replaced by a C# 15 union type: a deliberate breaking change on net11.0, with the TFM divergence it brings accepted by the owner. Apply the same pattern, and the same guard, to any other attribute whose Web Awesome type is a number/date/time union.
