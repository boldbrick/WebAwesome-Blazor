# WebAwesome.Blazor Technical Standards

The engineering standards and practices for authoring and maintaining the Web Awesome Blazor wrappers. This is the durable wrapper authoring contract; general C# style lives in `CLAUDE.md`, the upgrade pipeline and testing strategy in `docs\contributing\UPGRADE-PROCESS.md`, and contribution process in `CONTRIBUTING.md`. Task-specific plans and evaluations that shaped these standards are archived under `tasks\<epic>\<task>\`.

## Architecture principles

- **Pure C# render trees.** Wrappers are `ComponentBase` descendants implementing `BuildRenderTree` by hand — no `.razor` markup. This keeps attribute emission, event wiring, and sequence numbering under explicit control.
- **Web Awesome components are self-contained.** The upstream web components handle their own initialization, internal state, DOM manipulation, and third-party library integrations. A wrapper renders the correct tag with the correct attributes, slots, and event subscriptions — nothing more. Never re-implement behavior the custom element already provides.
- **Naming**: tag `wa-foo-bar` → class `WaFooBar`, one class per file in `src\WebAwesome.Blazor\Components\`. Web Awesome's CSS-only layout utilities (no `wa-*` element, just markup + classes) are wrapped as components too, in `src\WebAwesome.Blazor\Layouts\`. Shared infrastructure lives in `src\WebAwesome.Blazor\Base\`.
- **Completeness**: every documented attribute, event, slot, and method of the bound Web Awesome version has a wrapper counterpart (mechanically enforced — see the parity suite in `docs\contributing\UPGRADE-PROCESS.md`). Intentional deviations are recorded in `parity-config.json` with a reason, never silently.
- **Every element wrapper** exposes `[Parameter(CaptureUnmatchedValues = true)] AdditionalAttributes` pass-through and captures `ElementReference? Element`.

## Package split

The repository ships two packages with one version (design: `tasks\WA-3.14\WAB-49\datagrid-cell-rendering-design.md`, section 17.1):

- **`WebAwesome.Blazor`** (`src\WebAwesome.Blazor`) gets every feature that binds an upstream member, or a behavior that the upstream documentation describes. It stays pure bindings (the README non-goal), and it knows nothing about the Extensions package.
- **`WebAwesome.Blazor.Extensions`** (`src\WebAwesome.Blazor.Extensions`, tests in `src\WebAwesome.Blazor.Extensions.Tests`) gets every feature that adds behavior that upstream does not have. It connects to the bindings only through their public API and its own JS initializer `wwwroot\WebAwesome.Blazor.Extensions.lib.module.js`: no subclass of a wrapper, no new wrapper parameter. Its custom event types are registered there too, through `registerEventTypes` of the public module `webawesome-events.js`, and bound in C# (`[EventHandler]` in Extensions, the event passed through the wrapper's `AdditionalAttributes`).
- **Sister wrapper sets.** Another package that wraps custom elements of its own on top of the bindings (for example `waa-*` elements) builds on the public extension API, never on internals; see "Extension API" below.
- **One version.** Both projects take their version from `src\Version.props`. The Extensions package depends on `WebAwesome.Blazor` with a floor of its own version (a `ProjectReference`, which pack turns into that dependency); the release preflight gate `extensions-package` checks it in the nuspec.
- **Package docs.** A local Release build bundles the docs into both packages under `docs/` with DocPack (`src\DocPack.Build.props` and `.targets`, plugin-owned; the `docpack` tool is pinned in `.config\dotnet-tools.json`). The bundle has the API reference from the XML docs of the last target framework and a skill (`PACKAGE-SKILL.md` beside the project, or a generated one). The `DocPackContent` items of `WebAwesome.Blazor.csproj` add `docs/content/`: `docs\CHANGELOG.md`, `docs\technical\`, `docs\migration\` and the upstream Web Awesome docs. The target `WaStageUpstreamDocs` (`src\WebAwesome.Blazor\UpstreamDocs.targets`) copies the `*.md` files of `inputs\WebAwesome` (with the upstream `LICENSE.md`, without `ai\`) to `obj\...\docpack-content\web-awesome\` before the bundle. In that copy only, an inline task rewrites the site links outside code: a `/docs/...` link with a bundled page becomes a relative `.md` link, every other site-absolute link goes to `https://webawesome.com` (property `WaUpstreamSiteOrigin`), and a Nunjucks `{{ ... }}` link target takes its site variable value. `inputs\WebAwesome` stays a verbatim upstream copy. `docs\contributing\` and `docs\inspector\` (the documentation of a repository tool) stay out. `THIRD-PARTY-NOTICES.md` goes to the root of the main package with the bundle. `src\Directory.Build.props` turns DocPack off in Debug builds and on GitHub, so the nuget.org packages have no bundle. The release preflight gate `docs-bundle` checks the content, and `tools\release\Publish-WaLocalFeed.ps1` pushes the packages to the internal NuGet feed.
- **No manifest.** The Extensions package does not follow the custom-elements manifest: the API parity suite reads only `WebAwesome.Blazor`. Its public API snapshot (`approved-extensions-public-api.txt`) and its own tests cover it, and every upgrade builds and tests it with the rest of the solution.

## Extension API

A sister wrapper set (a package with wrappers of its own custom elements, on top of `WebAwesome.Blazor`) uses the same rendering infrastructure as the library's wrappers. Since 3.14.0.3 it is public, in the namespace `WebAwesome.Blazor.Infrastructure` (folder `src\WebAwesome.Blazor\Infrastructure\`) and in `wwwroot\webawesome-events.js`; `PACKAGE.md` ("Building a sister wrapper set") documents it for the consumer with examples. The namespace is for the authors of wrappers and extension libraries: app code imports `WebAwesome.Blazor.Base` for the form bases and the capability interfaces and does not need `Infrastructure`, so the render tree and change-event extension methods stay out of its IntelliSense. Every wrapper and base of the library imports it explicitly.

- **Sticky attributes.** `RenderTreeBuilderExtensions.OpenWaElement(this, 0, "xyz-x")` opens the element (with the inspector metadata, also for a wrapper type outside the library) and returns the component's `WaAttributeMemory`; every sticky overload takes it with the element default as a `Default<Name>` constant (see the sticky rule under "Render tree discipline").
- **Own events.** `AddOwnEventIfHasDelegate` (generic and non-generic) adds the handler only with a delegate and Blazor's `stopPropagation` always, whatever the prefix: the `onwa-` rule of `AddAttributeIfHasDelegate` for any own event (`onwaa-selection-change`). There is no prefix registry; `AddAttributeIfHasDelegate` and `AddOwnEventStopPropagation` stay keyed on `onwa-`. The JS side is `registerEventTypes(blazor, definitions)` of `webawesome-events.js` (name to `createEventArgs`, `null` for `detailArgs`, or `{ createEventArgs, browserEventName }`), called from the package's own `<PackageId>.lib.module.js` in `afterWebStarted`/`afterStarted`; it registers each name once and skips a name already registered through the module (any copy: the set of names is on `globalThis[Symbol.for('WebAwesome.Blazor.eventTypes')]`) with one `console.warn`. The module also exports `sanitize`, `detailArgs` and `isoDate`. The C# side declares the events with `[EventHandler]` on a public static class `EventHandlers` (as `src\WebAwesome.Blazor.Extensions\DataGrid\EventHandlers.cs`), and the event args inherit `System.EventArgs`.
- **Size default of form controls.** A form control derived from `WaInputBase<TValue>` overrides `protected virtual WaSize? ElementDefaultSize` (default `DefaultSize`, medium) with its element's literal size default, or `null` when the element has none (`WaRadioGroup`): non-null renders `size` sticky with that default, `null` renders it plainly. `WaDatePickerBase` is no `WaInputBase` and keeps its own sticky `size` with the medium default of `wa-date-picker`.
- **Typed helpers.** `AddBooleanAttribute`, `AddTrueFalseAttribute`, `AddOnOffAttribute`, `AddDateAttribute`, `AddTimeAttribute`, `AddDateTimeOffsetAttribute`, `AddDateSetAttribute`, `AddDaysOfWeekAttribute` and their sticky overloads; the `CS0619` guards refuse a `bool` or a date or time on the generic paths with a message that names the helper to use. `ChangeEventArgsExtensions` (`GetStringValue`, `GetStringArrayValue`, `TryParseJsNumber`) reads the value of a change event as the library's form controls do; a multi-value control binds the array value of its `change` event as `WaSelect` does. `WaWireFormat` formats and parses the wire forms of dates, times, date ranges and lists (its shared separator arrays and the day slot name stay internal). `WaInputBase.FormatValidationMessage` is protected, so a typed control words a parse failure as the library does.
- **Form control clusters.** `FormControlRendering` renders the label cluster (`AddLabelAndHintAttributes`, `AddWithHintAndLabelAttributes`, `AddLabelAndHintSlots`) and the affix slots (`AddAffixSlots`) for a control that implements `IWaLabeledControl` or `IWaAffixedControl`. Its popup, clear, calendar and day content helpers stay internal: they bind Web Awesome's own `wa-*` events and relays or render the date elements' calendar options and day slots.
- **JSON of enums.** `WaEnumJsonConverter<TEnum>` is public: a sister set derives a sealed converter for its own enum with `ToWire` (usually `ToHtmlValue()`). The library's concrete converters stay internal.
- **Stays internal**, in the same namespace so that a later release can only change the visibility: `WaJsPropertyPush` (the property push), `WaInspectorMetadata`, `WaJsFunctionJsonConverter`. In `Base`: the `Constants` members (the helpers encapsulate them), the relay hooks of the bases (`RelaysKeyDown`, `AddRelayedKeyDownHandler`, `AddNumericInputHandler`, `RelaysPopupEvents`: the JS relay knows only `wa-*` hosts) and the `private protected` hooks of `WaSliderBase`, `WaDateInputBase` and `WaDatePickerBase`. The public docs name no internal type.
- **Proof**: the test-only sister set in `src\WebAwesome.Blazor.Extensions.Tests\SisterSet` (`xyz-chip`, `onxyz-remove`, two form controls with their own size defaults, an enum with its own JSON converter) uses only public members; that project has no `InternalsVisibleTo` from `WebAwesome.Blazor`. `EventsModuleContractTests` guards the exports of the JS module, and the public API snapshot records the surface.

## Render tree discipline

- **Constant sequence numbers, never `sequence++`.** Incrementing sequence numbers defeats Blazor's diffing and produces false-positive DOM changes. Number statically with gaps between sections (attributes, events, element ref, slots); gaps are fine. When a helper method builds a portion, pass it a constant base and number `sequence + 0`, `sequence + 1`, … inside.
- **Conditional emission via the shared extensions** (`Infrastructure\RenderTreeBuilderExtensions.cs`): `AddAttributeIfNotNullOrEmpty` / `AddAttributeIfNotNull` for attributes, `AddAttributeIfHasDelegate` for events. Booleans never go through `ToString()` (`AddAttributeIfNotNull` rejects them at compile time): a plain `bool` uses `builder.AddAttribute` (present or absent); a `bool?` for a Lit `type: Boolean` attribute uses `AddBooleanAttribute`; a `bool?` for an attribute with a `"true"`/`"false"` converter (check the component source, e.g. `spellcheck`) uses `AddTrueFalseAttribute`, which is also the only way to turn off an attribute whose Web Awesome default is true. Inline `if (X.HasDelegate)` guards are reserved for cases where the emitted callback differs from the guarded one (factory-wrapped handlers) or sequence numbers increment conditionally.
- **Numbers render in the invariant culture.** Blazor formats a non-string attribute value with the current culture, so `builder.AddAttribute(n, "distance", Distance)` renders `"0,5"` under cs-CZ, which Web Awesome can't parse. Pass a number through `AddNumberAttribute` (non-nullable; nothing while it holds the element default, see the sticky rule below) or `AddAttributeIfNotNull` (nullable); both format invariantly. Parse element values with `ChangeEventArgsExtensions.TryParseJsNumber`, and override `FormatValueAsString` with the invariant culture in a numeric `InputBase` wrapper. `RenderedAttributeParityTests` renders every wrapper under a hostile culture and fails on a culture-formatted value.
- **Dates and times render in Web Awesome's wire formats, never through `ToString()`.** The invariant default forms (`01/02/2026`, `13:04`) are not what the element parses, so `AddAttributeIfNotNull` and `AddNumberAttribute` reject `DateOnly`, `TimeOnly`, `DateTime` and `DateTimeOffset` at compile time (`CS0619`) and `FormatInvariant` throws for them. Use the dedicated helpers, backed by `Infrastructure\WaWireFormat` (which mirrors the element's parsers; re-verify it against the target version's `date-picker/internal/iso.ts`, `matchers.ts` and `time-input/internal/segments.ts`, and the day slot name against the date picker's `renderDay`, on every upgrade): `AddDateAttribute` (ISO `yyyy-MM-dd`), `AddTimeAttribute` (a bound: `HH:mm`, or `HH:mm:ss` with seconds), `AddDateSetAttribute` (ascending ISO dates, space-separated), `AddDaysOfWeekAttribute` (`sun`..`sat`, Sunday first) and `AddDateTimeOffsetAttribute` (`yyyy-MM-ddTHH:mm:ss.fff+hh:mm`, the ECMAScript form `new Date()` reads as one instant). A typed `InputBase` wrapper must override **both** `FormatValueAsString` (the base uses the culture-sensitive `ToString()`) and `TryParseValueFromString`: format exactly as the element emits (a time follows the step rule), parse strictly (`""` binds `null`), and report a failure with a `Constants.*ValidationMessageFormat` through `FormatValidationMessage`. `RenderedAttributeParityTests` (h) checks every sampled date, time, instant, range and set attribute against Web Awesome's own patterns (`WaWirePatterns`).
- **An unset parameter emits no attribute**, so the Web Awesome default applies — wrappers never bake upstream defaults into C#, and a non-nullable parameter holding the element default renders nothing either.
- **Sticky attributes: a rendered attribute is never removed again, and its default is explicit at the call site.** When Blazor removes an attribute, Lit's converter sets the element property to null, not back to its default (a `wa-slider` whose max returns from 50 to the default 100 would get `max = null`, which its arithmetic reads as 0; a tooltip's distance null instead of 8). So every attribute of the wrapper's element that has a literal element default goes through the per-component `Infrastructure\WaAttributeMemory`, and the call site passes that default, always as the wrapper's public `Default<Name>` constant: open the element with `var attributes = builder.OpenWaElement(this, 0, "wa-x");` and write `builder.AddNumberAttribute(attributes, 10, "feedback-duration", FeedbackDuration, DefaultFeedbackDuration);`, `builder.AddAttributeIfNotNull(attributes, 11, "tooltip-placement", TooltipPlacement?.ToHtmlValue(), DefaultTooltipPlacement.ToHtmlValue());` or `builder.AddDefaultedAttribute(attributes, 12, "tooltip", Tooltip.ToHtmlValue(), DefaultTooltip.ToHtmlValue());` (every sticky overload, typed ones included, takes the default right after the value; base-class helpers use `WaAttributeMemory.Of(this)`). The memory renders nothing while the parameter is null (nullable) or has never differed from the passed default (non-nullable), the value when it is set, and once the attribute has been rendered, a return to null or to the default renders the passed default explicitly. The library holds no table of defaults and looks nothing up. An attribute whose CEM default is none uses the plain overload without `attributes` and without a default, since removal restores the unset state; plain booleans keep Blazor's present/absent rendering (a removed Lit boolean reads false, its default; a `"true"`/`"false"` converter attribute defaulting to true, `spellcheck`, is sticky with `DefaultSpellcheck = true`). A default computed when the element is set up (`date = new Date()` on `wa-relative-time` and `wa-format-date`) goes through the `TimeProvider` overload of `AddDateTimeOffsetAttribute`, which renders the clock's current instant once the attribute was rendered and the parameter returned to null. Where a shared renderer serves elements with different defaults, the default comes from the concrete wrapper (`WaChartBase.ElementDefaultType`, the overridable `WaInputBase.ElementDefaultSize`, the `disabledDatesDefault` argument of `FormControlRendering.AddCalendarAttributes`); defaults shared by a whole capability cluster live on its interface (`IWaLabeledControl.DefaultLabel`, `IWaCalendarOptions.DefaultMonths`). Never guard an attribute by hand with `if (X != default)`. The oracle is test-side: `src\WebAwesome.Blazor.Tests\ApiParity\WaElementDefaults.cs`, the CEM literal defaults, generated by `ElementDefaultsTableTests` (which fails when the file differs from the surface and writes the file to copy over it). `RenderedAttributeParityTests` checks against it: (i) re-renders every parameter back to its default on the same instance and requires the element default, (j) requires every `Default<Name>` constant to hold it, and (k) requires every default a sticky call site passes (recorded by the memory) to be it, and no default where the element has none; `sticky-attributes.spec.js` proves the rule on the element properties.
- **Editable values use explicit bindings** in the pattern of Blazor's built-in inputs: emit `value`, an `onchange` handler created with `EventCallback.Factory.CreateBinder`, and call `builder.SetUpdatesAttributeName("value")`. This is mandatory — Blazor's change binder special-cases native `INPUT`/`SELECT` elements only (e.g. it reads `.checked` solely for native checkboxes), so custom elements get no two-way binding for free.

## Public API conventions

The public API is C# — it must feel idiomatic to .NET consumers, not mirror DOM attribute spellings or JavaScript typing:

- **Natural PascalCase word splits**, not mechanical kebab-case conversion: `MaxLength` (not `Maxlength`), `SrcDoc`, `AllowFullScreen`, `AutoFocus`, `InputMode`. Each such rename is recorded in `parity-config.json` `attributeOverrides`.
- **Strong typing throughout.** Closed value sets become nullable C# enums in `Components\Enums.cs` (or `Layouts\Enums.cs`) with a `ToHtmlValue()` switch-expression extension: a union of string or number literals (`'a' | 'b'`, `1 | 2`, alias-resolved; `EnumValueParityTests.NoStringOrDecimalParameter_IsBoundToLiteralUnion` fails on a `string` or `decimal` parameter bound to one, allowlist `untypedLiteralUnionAttributes`), and a plain `string` the element reads as a closed token set (`sandbox`, `referrerpolicy`, `heading-level`), a `[Flags]` enum for a token list, recorded in `tokenListAttributes`. Existing enums (`WaSize`, `WaVariant`, `WaPlacement`, …) are reused whenever the value set matches, never duplicated. An enum that travels as JSON (event args, the data grid column model) carries a `[JsonConverter]` derived from `Infrastructure\WaEnumJsonConverter`, which writes and reads exactly its `ToHtmlValue()` strings and fails on an unknown one; a payload the JS initializer projects to a known shape is a record (`WaMutationRecord`, `WaResizeEntry`/`WaRect`, `WaElementInfo`), never `object[]`. A `number | 'any'` step is `WaValueStep?` (a positive number or `WaValueStep.Any`, implicit from the numeric literals Razor produces, invariant `ToString()`); an attribute read by an `"on"`/`"off"` converter (`autocorrect`) is `bool?` rendered by `AddOnOffAttribute` and listed in `onOffAttributes`. A list attribute is `IReadOnlyList<double>?`, `IReadOnlyList<string>?`, `IReadOnlySet<string>?` (ordinal order) or `IReadOnlyList<TEnum>?`, joined with exactly the separator the element splits it on (`AddNumberListAttribute`, `AddTokenListAttribute`, `AddTokenSetAttribute`; an item that would split, or a non-finite number, throws); cite the separator in `WaWirePatterns.ListSeparators`, which (h) reads the rendered list with. Where Web Awesome uses a string only for lack of a JS type, the parameter takes the .NET type and the wrapper converts it: a date is `DateOnly?`, a time of day `TimeOnly?`, an instant `DateTimeOffset?` (rendered with its offset; never `DateTime`, whose unspecified kind the browser would read as local time), a date range `WaDateRange?`, a set of dates or weekdays `IReadOnlySet<DateOnly>?`/`IReadOnlySet<DayOfWeek>?`. A null or empty collection renders no attribute. A string stays a string only where the value set is open (URLs, CSS lengths, BCP 47 locales, IANA time zones, colours).
- **A mode that changes the value's type is a wrapper of its own**, not a parameter: `WaDateInput`/`WaDatePicker` bind `DateOnly?`, `WaDateRangeInput`/`WaDateRangePicker` bind `WaDateRange?` and always render `mode="range"`, sharing their element's base class (the precedent is `WaRange` next to `WaSlider`).
- **Numbers**: properties measured in pixels or milliseconds are `int?`; `double?` only where fractional values are meaningful (e.g. animation iteration start).
- **Defaults are the element's.** A parameter's C# default is Web Awesome's default for the attribute (the CEM `default`): an optional parameter is nullable, defaults to `null` and renders nothing when unset, so the element's own default (including a localized label, or a variant inherited from an enclosing element) applies; a parameter that must be non-nullable carries exactly Web Awesome's default, declared as a named public constant `Default<Name>` on the wrapper (`WaCopyButton.DefaultFeedbackDuration`, `WaSlider.DefaultMax`) and used as its initializer, and renders nothing while it holds it (durations stay `int` milliseconds). A nullable parameter whose attribute has a literal element default declares its `Default<Name>` too (`WaCopyButton.DefaultTooltipPlacement`), a `static readonly` field where the type cannot be a constant (`WaValueStep`, a date or time, where null stands for the element's empty attribute, a collection), because its sticky call site passes it (see the sticky rule). Never choose a "nicer" default, and never skip rendering a value because it equals a C# default that differs from the element's, which makes that value unreachable (`WaDropdown.Distance = 8` rendered nothing, so an explicit 8 gave 0). `RenderedAttributeParityTests.BaselineRender_EmitsOnlyElementDefaults` (no CEM attribute renders unset, not even at its default, and a non-nullable parameter set to its default on the first render renders nothing), `ParameterDefaults_MatchTheElementDefaults` (the C# value consumers see, and its `Default<Name>` constant) and `DefaultConstants_MatchTheElementDefaults` (every `Default<Name>` against the oracle) enforce it; a default the CEM cannot express goes into `divergentParameterDefaults`, a structural reason to render one into `wrapperDefaultAttributes`, each with a reason.
- **Events**: `wa-x` → `[Parameter] EventCallback<TArgs> OnX`, with typed event args classes in `Components\EventArgs.cs` when the event carries a `detail`. Event args classes inherit `System.EventArgs` (the runtime rejects them at dispatch otherwise).
- **Element methods**: documented instance methods become `XxxAsync()` wrapper methods.
- **The public API snapshot is a change detector, not correctness coverage.** `PublicApiSnapshotTests` only proves the surface didn't change unnoticed; a promoted baseline says nothing about whether a member works (it enshrined every dead callback before 3.12.0). Correctness comes from the render-based parity checks and the browser specs.
- **Slots**: named slots → `RenderFragment` parameters (`XxxContent`), the default slot → `ChildContent`. Every slot the element declares gets one, and a wrapper renders content only into slots its element declares; `SlotParityTests` checks both directions on the rendered markup (a slot that genuinely cannot be a parameter goes into `unreachableSlots` with a reason). Wrap the fragment in an element carrying the `slot` attribute (a `span`, or a `div` for block content); where the slot lays out each slotted element as an item of its own (`wa-slider`'s `reference` labels), give that wrapper `style="display: contents"` (`Constants.TransparentSlotWrapperStyle`) so the fragment's elements become the items. A family of slots named after data (`day-YYYY-MM-DD`) is a host/sub-component pair instead, see "Dynamic slots".

## Event delivery contract

Binding a Web Awesome custom event requires two coordinated pieces; missing either fails silently (no build error, no runtime error, the event just never fires):

1. In the render tree, the event is bound under the **`on`-prefixed attribute name**: `builder.AddAttributeIfHasDelegate(seq, "onwa-show", OnShow)`.
2. The event name is **registered with `Blazor.registerCustomEventType`** in the JS initializer `src\WebAwesome.Blazor\wwwroot\WebAwesome.Blazor.lib.module.js`, which registers its lists through `registerEventTypes` of `webawesome-events.js` (see "Extension API") — in the plain `eventNames` list when the event's `detail` is JSON-safe and maps 1:1 onto the typed args, or with a `specialArgs` mapping when the detail carries DOM nodes or the typed args need derived values (payload shapes must stay in sync with `Components\EventArgs.cs`; deserialization is case-insensitive and ignores extra properties).

Only bind events the bound Web Awesome version actually emits (check the CEM and the component's `@event` JSDoc), and bind each `EventCallback` to the event its name stands for: `wa-after-hide` → `OnAfterHide`, `blur` → `OnBlur`, with deviations in `parity-config.json` `eventOverrides`. Native DOM events the CEM doesn't list (`click`, `focus`, `blur`, the keyboard events) are admitted through `nativeDomEvents`. A callback the wrapper raises from another handler (e.g. `OnCheckedChange` from the value binding's `change`) goes into `derivedEventCallbacks`. Number-valued elements bind the `onnumericchange`/`onnumericinput` aliases (`Constants.*EventAttribute`) instead of `onchange`/`oninput`.

**Where Blazor listens.** Blazor delivers a custom event (and a bubbling built-in such as `keydown`) only as it bubbles to the document, and a non-bubbling built-in (`focus`, `blur`) only to `composedPath()[0]`, the innermost element. An event that never gets there is dropped silently, even with a correct binding and registration:

- **Focus**: bind `OnFocus`/`OnBlur` to the bubbling, composed `onfocusin`/`onfocusout` wherever the focus can land inside the shadow root (every `WaInputBase` control, `WaButton`, `WaFileInput`); `FocusEventArgs.Type` is then `"focusin"`/`"focusout"`. A focus move between two parts of the same shadow root (OTP segments, the thumbs of a range slider) is not dispatched outside it, so it raises nothing; a move between the control and content slotted into it (one radio of a group to the next, a select's input into its option list) raises `OnBlur` then `OnFocus`, which the callback docs state. Keep `onfocus`/`onblur` only where the host itself takes the focus (`WaRadio`, `WaTab`, `WaDropdownItem`): there `focusin` would also arrive from nested items (submenus). The checks treat `focusin`/`focusout` as the element's `focus`/`blur` through `bubblingEventAliases`.
- **Own events only**: Web Awesome's `wa-*` events bubble, and Blazor calls every handler for an event on the way up, so a nested component's event would also reach the outer wrapper's callback of the same name (a `WaSelect` closing inside a `WaDialog` raised `WaDialog.OnHide`, which closed the dialog). `RenderTreeBuilderExtensions.AddAttributeIfHasDelegate` therefore adds Blazor's `stopPropagation` for every `onwa-*` name it is given, **whether or not the callback is set** (`Constants.WaEventAttributePrefix`): each wrapper consumes its element's own events. A handler bound another way (`WaTabGroup`'s `onwa-tab-show`) adds `AddOwnEventStopPropagation` itself. A sister wrapper set binds its own events (another prefix) with `AddOwnEventIfHasDelegate`, which stops them whatever the prefix. Blazor's `stopPropagation` only ends Blazor's own dispatch; Web Awesome and page listeners still see the event. A plain element's `@onwa-*` handler no longer receives the events of the wrappers inside it. `EventBindingRegistrationTests.WaEventHandlers_StopAtTheirOwnWrapper` checks every wrapper, `NestedEventPropagationTests` the dispatch.
- **Non-bubbling or stopped events**: an element event that does not bubble (`wa-color-picker`'s popup events, `wa-intersect`) or whose propagation the element stops in its shadow root (`keydown` in `wa-select`, `wa-combobox`, `wa-color-picker`) is **relayed** by the JS initializer. Add an entry to its `relayedEvents` map (private Blazor name → `{ event, hosts, source }`, `source: 'host'` when only the host's own dispatch counts, `'subtree'` for native events from inside it), a `Constants.Relayed*EventAttribute` with the `on`-prefixed private name, and bind it with `AddRelayedEventIfHasDelegate`, never `AddAttributeIfHasDelegate`: the relayed event bubbles, and the helper adds Blazor's `stopPropagation` so it reaches no other wrapper of the same element further up. A capture-phase listener on the document re-dispatches each original event once, as a bubbling, composed `CustomEvent` under the private name on its host; the payload is the original event's (`specialArgs`, the sanitized detail, or Blazor's keyboard shape), and the original is left untouched, so page listeners never see a second `wa-*` event. A `WaInputBase` wrapper relays its keydown by overriding `RelaysKeyDown` and calling `AddRelayedKeyDownHandler`. Each upgrade, check the component sources for `bubbles: false`, plain `new CustomEvent(` dispatches and `stopPropagation()` in keyboard handlers.

Two test classes enforce the contract on the **rendered** output, not the source text: `RenderedWrapperCatalog` renders every wrapper with bUnit, once per `EventCallback` with a no-op delegate, and reads the handler names (and Blazor `stopPropagation` directives) on the root element from the render tree. `EventCallbackBindingParityTests` compares them with the CEM events of the tag the wrapper renders, resolving aliases, relays and `bubblingEventAliases` to the event they stand for. `EventBindingRegistrationTests` compares them with the JS initializer's registrations, in both directions: a relayed name must be private, have its constant, be bound only on its hosts and always with `stopPropagation`. Neither can see whether an event reaches Blazor in a real browser; only the e2e dispatch specs prove that, so every callback needs one (`event-coverage.spec.js`).

**DOM ownership.** Blazor removes the elements it renders itself (`parentNode.removeChild`) and inserts new nodes next to the ones it tracks, so a rendered element must never leave the DOM behind its back: the next render fails ("Cannot read properties of null (reading 'removeChild')"). Web Awesome removes a toast item once it has hidden (`wa-toast` in its `wa-after-hide` handler, `wa-toast-item` right after dispatching it). `WaToastItem` therefore renders the marker `Constants.BlazorOwnedAttribute`, and the JS initializer (`installOwnershipGuard`), in a capture-phase `wa-after-hide` listener on the document, replaces `remove()` on a marked element with hiding it in place (the `hidden` attribute) and closes a stack left with only such items; Blazor removes the element when the model drops the item in `OnAfterHide`. Toast items `wa-toast` creates itself (`create()`) carry no marker and are removed as before. `wa-carousel`'s `addSlide()`/`removeSlide()` move and remove a slide by design, so they are not wrapped (`ignoredMethods` in the parity config); slides come from the model (`@foreach` with `@key`), which `carousel-slides.spec.js` covers, and the element's own loop clones are nodes it created itself. Each upgrade, check the component sources for `this.remove()` and for removals or moves of light-DOM children (`.remove()`, `removeChild`, `replaceChildren`, `replaceWith`, `innerHTML`, `append`/`insertBefore` of an existing node); a node Web Awesome created itself is harmless.

## Icon slot convenience

Components exposing an icon-shaped slot — a `start`/`end` slot documented as accepting "an element such as `wa-icon`", or a dedicated `*-icon` slot (`expand-icon`, `copy-icon`, …) — get a `<Slot>IconName` string parameter (`StartIconName`, `ExpandIconName`, …) alongside the slot's `RenderFragment`:

- Rendering goes through `RenderTreeBuilderExtensions.AddIconSlot(builder, sequence, slotName, iconName)`, which emits a `wa-icon` with a `name` attribute (and `slot` when not the default) for a non-empty name.
- **Fragment wins**: when the slot has a `RenderFragment` counterpart, the icon parameter renders only while that fragment is `null`; the parameter's doc comment states "Convenience alternative to `<FragmentName>`; ignored when the fragment is set."
- Pane-like `start`/`end` slots holding arbitrary panel content (e.g. split-panel panes) are excluded from this convention.

## Dynamic slots

A slot whose name Web Awesome builds from data, one per value (`wa-date-input`/`wa-date-picker` `day-YYYY-MM-DD`, one per date), cannot be a fixed `RenderFragment` parameter. Expose such a family as a host/sub-component pair, following `WaDayContent`:

- **The sub-component** takes the typed key as `[Parameter, EditorRequired]` (a `DateOnly`, never a string) and its `ChildContent`, and renders `<span slot="…">` around the content, nothing when the content is null. The name is formatted through `WaWireFormat` exactly as the element builds it, culture-free (`FormatDaySlotName`: `day-` and `formatIsoDate`, as the date picker's `renderDay` does).
- **The host** (the element wrapper's base: `WaDateInputBase`, `WaDatePickerBase`) takes a `ChildContent`, documented as being for the sub-component when the element has no default slot, and renders it directly inside the element through a helper (`FormControlRendering.AddDayContent`) that wraps it in a **fixed** (`IsFixed`) `CascadingValue` of a small internal host interface (`IWaDayContentHost`). The cascading value renders no DOM, so each span is a direct child of the element, as a slot assignment requires; being fixed, it adds no re-render subscriptions.
- **Placement is enforced**: without a cascaded host (outside the host, or inside the content of another slot, where the span would not be a direct child), the sub-component throws `InvalidOperationException` naming the hosts.
- **Registration**: the sub-component tells its host when its slot appears, moves to another key or disappears (from `OnParametersSet` and `Dispose`). A host acts on it only where its element needs it. `wa-date-picker` renders the slot in every cell, so the browser assigns content added at any time. `wa-date-input` forwards the day slots to its inner calendar only on its first update and on its default slot's `slotchange`, which a day-slotted child never causes, so `WaDateInputBase` fires that `slotchange` after its next render (`signalDefaultSlotChange` in the interop module: an empty text node appended and removed), rendering itself when the change came from a component that rendered on its own. Prefer such a nudge of the element's own mechanism to reimplementing it, and re-verify the element's forwarding in the source every upgrade (`updateForwardedDaySlots`); `day-content.spec.js` fails when it breaks.
- **Duplicates are not rejected**: every element assigned to one slot name is shown, in document order, so two contents for one key both show; the sub-component's docs say so.
- **Per-cell callbacks** (`dayContent`, `isDateDisabled`) are no .NET callbacks, which would need a JS round-trip per rendered cell: the hosts bind them as JavaScript functions (`DayContentFunction`, `IsDateDisabledFunction`, see "JavaScript function references"). A `WaDayContent` for a date wins over `dayContent` for that date.
- **Parity**: `SlotParityTests` resolves a rendered name against a patterned CEM slot name (the whole `-`-separated segments `YYYY`, `MM`, `DD` match digits; add a placeholder to `SlotNamePlaceholders` for a new kind of key), samples the host's `ChildContent` as the sub-component holding the probe (`FragmentSample`), and counts a `sourceVerifiedSlots` entry as declared where the CEM omits a slot the source renders (`wa-date-picker`'s day slots; the entry goes stale once a CEM declares it). A new sub-component goes into `RenderedWrapperCatalog.HostedSlotContentComponents`, since it cannot render on its own.

## JavaScript interop

The entire JS surface of `WebAwesome.Blazor` is deliberately four small files (the Extensions package brings its own initializer, see "Package split"); there are no per-component JS modules, no `document.getElementById` lookups, and no library-generated element ids:

- **`webawesome-interop.js`** — an ES module lazily imported by the `WebAwesomeJSInterop` service (`Base\WebAwesomeJSInterop.cs`). Everything is driven by `ElementReference`: generic `invokeMethod` / `getProperty` / `setProperty`, `setCustomValidity`, `signalDefaultSlotChange` (see "Dynamic slots"), and Web Awesome's module-level helpers (icon library registration, default icon family, kit code). Those helpers are imported from the entry point the page itself loaded (its Web Awesome script tag, or the configured `WebAwesomeOptions` loader URL when there is none): the registry is module state, and another copy or version of Web Awesome would hold a registry no `wa-icon` reads. `invokeMethod` waits for `customElements.whenDefined` (at most `elementDefinitionTimeoutMs`, 10 s) when the element is not defined yet: the autoloader imports the module of an element only after it finds the element in the DOM, so a wrapper method called soon after the first render can arrive first. After the wait an element that is still not defined fails with an error that names it. `InteropModuleContractTests` checks that every invoked identifier is exported. `JSDisconnectedException` is swallowed (returning a default where a value is expected) — circuits legitimately disconnect.
- **`WebAwesome.Blazor.lib.module.js`** — the Blazor JS initializer, auto-loaded by the runtime, whose jobs are custom-event registration, the relay of events Blazor cannot receive where Web Awesome dispatches them (see the event delivery contract above), and keeping Blazor-owned toast items in the DOM until Blazor removes them (DOM ownership, above).
- **`webawesome-events.js`** — the public module of the custom event types: `registerEventTypes` (once per name, a duplicate skipped with a warning, the names shared on a `Symbol.for` key) and the payload helpers `sanitize`, `detailArgs` and `isoDate`. The initializer registers its lists through it; the Extensions package and sister wrapper sets import it by path (see "Extension API"). `EventsModuleContractTests` guards its exports.
- **`webawesome-functions.js`** — the public module of the JavaScript function references (`WaJsFunction`): the shared function registry, `registerFunction`, `registerContextDecorator` and the resolver. The interop module imports it (its `setElementFunction`, `setDataGridColumns` and `registerIconLibrary` use the resolver); apps and the Extensions package import it by path. See "JavaScript function references" below.

Rules:

- **Interop is a last resort.** Prefer attribute binding; add an `XxxAsync` method only for element methods the CEM documents (or allowlisted in `parity-config.json` `extraElementMethods` with a reason — these allowlisted names are invisible to the CEM diff and must be re-verified against upstream source every upgrade). Never call methods that merely duplicate an attribute (`show()`/`hide()` vs. an `Open` parameter).
- Method wrappers guard a null `Element` (component not yet rendered).
- **A model sent as JSON leaves out its unset members.** Mark each nullable member of a model that goes to the element (the data grid column model, `WaDataGridFilterOption`) with `[JsonIgnore(Condition = JsonIgnoreCondition.WhenWritingNull)]`, so the element applies its own default. Use the attribute, not serializer options: the options of the Blazor JS interop have no global ignore condition. `WaDataGridColumnJsonTests` reads the JSON the interop sends.
- **A JS property that makes the element render again is pushed only on change.** `WaDataGrid` pushes `columns` on its first render, and later only when the serialized columns differ from the last push: the JSON alone decides, so a change in place is pushed and a new list with the same definitions is not. The push sends that JSON text to `setDataGridColumns`, which keeps the last JSON and the resolved columns per grid (a `WeakMap`) and assigns nothing for the same JSON. `data` is pushed on every parameter set (through `setDataGridData`, see "The data grid members"), so a list changed in place reaches the element. The function-valued element members (the grid's own too) and `ShadowStyles` follow the same rule through one helper, `Infrastructure\WaJsPropertyPush`: after each render it compares the descriptor JSON (or the CSS text) with its last push and calls the interop function only on a change; a value that was never set sends nothing.
- New .NET JS-interop APIs replace the module only if they can address a DOM element directly; `ElementReference` is not an `IJSObjectReference`, so the module stays (standing verdict: `tasks\WA-3.0\WAB-7\net10-blazor-evaluation.md`).

## JavaScript function references

A Web Awesome member that takes a JavaScript function (a data grid `formatter`, a select `getTag`, an icon library `mutator`, ...) is bound with a `WaJsFunction` reference (`Models\WaJsFunction.cs`, design `tasks\WA-3.14\WAB-49\datagrid-cell-rendering-design.md`, sections 5, 8 and 17). A function cannot cross the JS interop boundary, and the library never evaluates text as code (no `eval`, no `new Function`, no JavaScript source in C#; `FunctionsModuleContractTests` scans the library JavaScript for it), so the reference names a function and the browser resolves it:

- **Three kinds.** `WaJsFunction.Registered(name)` names a function the app registered with `registerFunction(name, fn)` of `_content/WebAwesome.Blazor/webawesome-functions.js`, for example in the app's own JS initializer (`beforeWebStart`/`beforeStart`, so it exists before the first render; a reference waits one animation frame and then up to 2 s for a late registration). Names are global for the page: an app uses its own prefix (`myapp.state`), the packages use `wab.`. `WaJsFunction.Module(url, exportName = "default", allowCrossOrigin = false)` names an export of an ES module, usually a collocated `Page.razor.js` (served at `./Pages/Page.razor.js`, or `./_content/<Library>/...` in a class library); each module is imported once per absolute URL. `WaJsFunction.Global(path)` names a function on a global dotted path, called with its owner as `this`.
- **Arguments and tags.** `WithArgs(object)` serializes its value at once (web defaults: camelCase) and the function receives it as `ctx.args`; `Uses(params string[])` declares the `wa-*` elements the function renders. Both return a copy: a reference is immutable, and its equality compares the descriptor.
- **Validation.** C# checks what it can: a name or export name is non-empty and trimmed, a global path is a dotted list of identifiers, a tag is a lowercase `wa-` name, a module URL has no whitespace or control character and is relative or `http`/`https` (`javascript:`, `data:`, `blob:` are rejected). Only the browser knows the page origin, so the resolver refuses a module of another origin unless the reference has `allowCrossOrigin` (decision D7).
- **Wire format.** The converter (`Infrastructure\WaJsFunctionJsonConverter.cs`) writes `{"$wab":"fn","ref":{...},"args":...,"uses":[...]}`, with `ref` one of `{"kind":"registered","name"}`, `{"kind":"module","url","export"}` (plus `"allowCrossOrigin":true`) and `{"kind":"global","path"}`; `args` and `uses` are left out when unset. The resolver looks for the marker only on the members it binds; row data is never examined.
- **Naming (decision D2).** A function-valued member never changes the type of an existing member. A data grid column member takes the upstream name where that is free (`Formatter`, `AggregatedFormatter`), else `<Name>Function` (`ComparatorFunction`, `ValueFunction`, `FilterFunction` for `filterFn`, and the function forms `FooterFunction`, `AggregationFunction`, `CellClassFunction`). An element member is always a `[Parameter]` named `<Name>Function`, because the natural names are taken or read as something else (`GetTag`, `ValueFormatter` and `HrefTemplate` exist; `GetSymbol` reads as a method, `Filter` as a filter text, `IsDateDisabled` as a flag, `DayContent` as the slot content): `GetTagFunction`, `FilterFunction`, `GetSymbolFunction`, `ValueFormatterFunction`, `IsDateDisabledFunction`, `DayContentFunction`, `HrefTemplateFunction`, and on `WaDataGrid` `RowClassFunction`, `RowDetailFunction`, `SearchFunction` (`searchFn`), `SelectableRowsFunction`, `ChildRowsFunction`.
- **Static and function form (conflict rule).** Where a static form of the same upstream member exists (`WaPagination.HrefTemplate`, `WaDataGrid.ChildRows`, and on a column `Footer`, `Aggregation`, `CellClass`), the wrapper throws `InvalidOperationException` in `OnParametersSet` when both forms are set, naming both (for a column also its id or field): both write the same property, and a silent precedence would hide the mistake. The icon library follows the same rule with `ArgumentException`. A column sends either form under the one upstream JSON key: the model marks both forms `[JsonIgnore]`, and one private `[JsonInclude]` property per key writes the form that is set; the interop resolves only a descriptor, so a static string under the same key stays as it is. An options class follows the same rule (`IconLibraryOptions.ResolverFunction` and `MutatorFunction`, because `Resolver` and `Mutator` exist). Each member's docs give the call as `(<upstream arguments>, ctx)` and the upstream return type.
- **Element members.** A wrapper pushes each `WaJsFunction?` parameter after the render (`WaJsPropertyPush.PushFunctionAsync`, only on change) to `setElementFunction(element, member, json)` of the interop module, which returns at once and does the rest in the browser: it waits for `customElements.whenDefined`, resolves the descriptor with `binding = { element, member, label, arity }` (so `ctx` holds `args` and `element`), registers the `Uses` tags of a member that renders, keeps the element's own value of the member before the first assignment, assigns the function, and runs `discover()` on the rendered output. Null gives the element its own value again (its default renderer, `''` for `hrefTemplate`), but only while the element still holds the assigned function, so an attribute that wrote the same property meanwhile wins. A reference that does not resolve leaves the element's own value. The `elementFunctions` table in `webawesome-interop.js` lists per tag each member with the number of arguments the element passes, whether its output renders in the shadow root, and the argument that holds the row (`rowArgument`); `elementFunctionContexts` adds per tag the `ctx` members beyond `args` and `element` (the grid: `grid`, and `rowKey` for a member with a row argument). `ElementJsPropertyTests` compares the table with the wrappers' parameters in both directions.
- **Binding a column member.** The model property is `WaJsFunction?` with `[JsonPropertyName("<upstream key>")]` and `JsonIgnore(WhenWritingNull)`. The wrapper sends the JSON to an interop function of the member's element (the grid: `setDataGridColumns`), which, for each descriptor, calls `resolveFunction(descriptor, binding)` of `webawesome-functions.js` with `binding = { element, member, label, arity, context, rowKey }`: `arity` is the number of arguments the element passes, so `ctx` always follows them (`dataGridColumnFunctions`: formatter 2, aggregatedFormatter 2, comparator 4, value 1, filterFn 3, footer 1, aggregation 2, cellClass 2); `context` adds the member's own `ctx` members; `rowKey` reads the row key of a call (members with a row argument: formatter, value, filterFn, cellClass). Then it registers the declared tags (`discover()` through `importWebAwesome` on a detached element with `data-wa-preload`, so the page's own Web Awesome instance registers them, before the assignment) and assigns the property. Content in a shadow root is invisible to the autoloader, so a member that renders content also calls `discover(element.shadowRoot)` after `updateComplete`; it registers only the tags of the rows rendered then, which is why `Uses` exists.
- **The data grid members.** Column members (through `setDataGridColumns`): `Formatter`, `AggregatedFormatter`, `ComparatorFunction`, `ValueFunction` (`value`: the computed value drives sort, filter, search, copy and the CSV export; give the column an `Id`), `FilterFunction` (`filterFn`, only with `Filterable`), `FooterFunction` (`footer`, the filtered rows of every page), `AggregationFunction` (`aggregation`) and `CellClassFunction` (`cellClass`). Grid members (`[Parameter]`s through `setElementFunction`, pushed on change): `RowClassFunction`, `RowDetailFunction`, `SearchFunction`, `SelectableRowsFunction` and `ChildRowsFunction`. `dataSource` is not bound: server mode with `OnDataRequest` covers it. Everything these functions produce is in the grid's shadow root: the cells, the footer cells (`footer-cell`), the detail panel (`row-detail`) and the row element that carries the `rowClass` classes, so `ShadowStyles` styles all of it. The footer is rendered when the columns are assigned, so `discover()` sees its elements; a detail panel renders only when its row expands, after that discovery, so its elements need `Uses`. WA 3.14.0 reads `childRows` only when the grid receives its data (its row model is keyed on the data). So on the first render `WaDataGrid` sends its function members before the data, and `setDataGridData` of the interop module waits for the function members of the grid that are still resolving (`setElementFunction` keeps a pending promise per element; a reference that does not resolve also ends the wait) before it assigns `data`; a newer data push replaces a waiting one. The columns need no wait: the row model does not depend on them. A `ChildRowsFunction` that changes after the data applies from the next `Data` push, the upstream limit (a `NOTE checked against WA 3.14.0` in the arity table; recheck on each upgrade).
- **Icon library members (decision D3).** `IconLibraryOptions.ResolverFunction` and `MutatorFunction` go to `registerIconLibrary` of the interop module inside the options JSON (keys `resolverFunction`, `mutatorFunction`), which resolves them with `binding = { member, label, arity }` and `context: { library }` before it calls Web Awesome's `registerIconLibrary`. `ctx` holds `args` and `library` (the library name), not `element`: a library has no element, and the mutator gets the `wa-icon` as its second argument. The resolved function returns what the referenced one returns, so a resolver can return a Promise, and with `SpriteSheet` a sprite reference. A resolver is a URL template (`Resolver`) or a function, never both, and the obsolete global path `Mutator` cannot be set with `MutatorFunction`: `WebAwesomeJSInterop.RegisterIconLibraryAsync` throws `ArgumentException`. A resolver function that does not resolve fails the registration (`InvalidOperationException`), because a library without a resolver draws nothing; a mutator function that does not resolve is left out, as the general rule says. `Uses` has no effect on these members. The arities are in `iconLibraryFunctions` of `webawesome-interop.js` (resolver 4, mutator 2).
- **Configuration.** A `WaJsFunction` never comes from configuration: it has no public constructor, and its converter writes only. An options class that holds one can still be bound for its other members (the binder leaves a missing key alone); the app makes the reference in code, for example `WaJsFunction.Registered(configuration["Icons:Resolver"])`, so the factory validates the configured text. The library itself binds only `WebAwesomeOptions` from configuration.
- **Shadow styles (decision D10).** A function renders its output in the element's shadow root, where page CSS does not reach. So the wrappers whose function members render app content take `ShadowStyles`, a CSS string (`WaDataGrid`, `WaSelect`, `WaCombobox`, `WaRating`, `WaDatePickerBase`, `WaDateInputBase`), and only those. `WaJsPropertyPush.PushShadowStylesAsync` sends a changed text to `setShadowStyles(element, css)`, which, after `whenDefined` and `updateComplete`, adds one constructed `CSSStyleSheet` per element to `shadowRoot.adoptedStyleSheets`, replaces its content when the text changes, and removes it for null or an empty text. `wa-date-input` renders its day cells in the shadow root of its own `wa-date-picker`, so the sheet goes into that shadow root too (`nestedShadowHosts`, which also feeds `discover()`). The docs of each parameter say what it is for: the classes of the app's own function output, not Web Awesome's internals, which `::part` and the CSS custom properties style.
- **Failure.** A reference that does not resolve (an unknown name after the wait, a module that does not load, a missing export, a path that names no function, another origin) makes `resolveFunction` return `undefined` after one `console.error` that names the member and the reference. The interop function leaves the member out, so the element applies its own default (the grid shows raw values, renders the aggregate through the formatter, sorts with its built-in sort) and keeps working. An exception the function itself throws is application code and is not caught.
- **The call and `ctx`.** The resolved function calls the referenced one with the element's arguments in their order and a trailing `ctx`, so an upstream example works unchanged. `ctx.args` and `ctx.element` exist for every member; the grid adds `ctx.grid`, a column member `ctx.column` (the column id), and a member with a row argument `ctx.rowKey` (the row's value of the grid's `row-key` field, as the grid's `getRowId` reads it). `ctx` exists once per call, so that a decorator member knows the row; to keep it cheap, the fixed members sit on a prototype built once per resolved function, the object holds only the call arguments, `rowKey` is a lazy getter, and the wrapper has fixed parameters per arity. Measured in Node 24 over 10,000 rows: about 20–30 ns per call above a direct call, about 50 ns when the function reads `ctx.rowKey`.
- **The registry and decorators.** The registry is shared state on `globalThis[Symbol.for('WebAwesome.Blazor.functions')]` (`{ functions: Map, decorators: [], listeners: Set }`, the list replaced on change, never changed in place), so two copies of the module (another base path, another version) share it; keep the shape compatible. `registerContextDecorator(decorator)` adds `ctx` members: the resolver calls `decorator(proto, binding)` once per resolved function before its first call (again when the decorator list changes), with `binding = { element, member, label, reference, args, rowArgument }` (`rowArgument` is the index of the call argument that holds the row, from the arity tables; undefined for a member without a row, such as `footer`); a decorator defines methods or getters on `proto`, which read the call through `this` (`this.args`, `this[callArguments]`, where `callArguments` is the exported `Symbol.for('WebAwesome.Blazor.callArguments')`). A decorator that throws is logged and skipped. The Extensions package adds its `ctx` helpers this way, from its JS initializer (`import ... from '../WebAwesome.Blazor/webawesome-functions.js'`), and its presets are `WaJsFunction.Registered` references to functions it registers.
- **Security.** A module URL comes from C# code, never from row data. The function is application code: `ctx.args` and the row are data, and a function that writes `innerHTML` must escape them; the library writes no HTML.
- **Tests.** `WaJsFunctionTests` (descriptor, validation, equality), `WaDataGridColumnJsonTests` (the JSON the grid sends), `WaDataGridIntegrationTests` (the push rule), `ElementJsPropertyTests` (every element member and `ShadowStyles` parameter, the arity table, the push rule), `FunctionsModuleContractTests` (the module exports and the shared symbols), `tools\e2e\tests\js-functions.spec.js` (the resolver without a grid on the free CDN, the grid members with Pro assets) and `tools\e2e\tests\element-functions.spec.js` (each element member in a real element, `ShadowStyles`, the removal of a function), `WebAwesomeJSInteropIconTests` (the icon library validation and JSON) and `tools\e2e\tests\icon-library-functions.spec.js` (the icon library resolver and mutator in a real `wa-icon`, on the free CDN), `tools\e2e\tests\grid-functions.spec.js` (the data grid members of phase 2 in a real grid, Pro).
- **Upgrades.** The arities in `dataGridColumnFunctions`, `elementFunctions` and `iconLibraryFunctions` come from the components' `.d.ts` files (`components\icon\library.d.ts` for the icon library); Phase 2 of every upgrade checks them again (`docs\contributing\UPGRADE-PROCESS.md`), and a new function-valued member gets a `<Name>Function` parameter and a table entry.

## Cell presets and cell actions (Extensions)

The data grid presets of `WebAwesome.Blazor.Extensions` (namespace `WebAwesome.Blazor.Extensions.DataGrid`, design `tasks\WA-3.14\WAB-49\datagrid-cell-rendering-design.md`, sections 6, 7, 8.4, 9 and 11) are plain function references: the main package knows no preset.

- **A preset is a registered function.** A factory of `WaDataGridFormatters` (cells), `WaDataGridComparators` (sort), `WaDataGridClassRules` (`CellClassFunction`, `RowClassFunction`), `WaDataGridFooters` (`FooterFunction`), `WaDataGridSearch` (`SearchFunction`) or `WaDataGridRows` (`RowDetailFunction`, `SelectableRowsFunction`) returns `WaJsFunction.Registered("wab.dataGrid.<preset>")` with its options as `WithArgs` and its elements as `Uses`. The names live in `DataGrid\PresetNames.cs` and in the `presets` table of `wwwroot\data-grid-presets.js`, which the Extensions initializer registers in `beforeWebStart`/`beforeStart`; `PresetScriptContractTests` compares both lists. A new preset needs both entries and its descriptor test.
- **Options.** A factory writes only the options that are set (`PresetArgs`), under the names the preset function reads, enums as their JavaScript strings, map keys verbatim (the serializer has no dictionary key policy). C# validates what it can (digit ranges, currency codes, unit identifiers, templates, URL schemes) and throws `ArgumentException`; the browser applies the options. `culture` is the name of the given culture, else `CultureInfo.CurrentCulture` when the factory runs, never the browser locale; the invariant culture is written as `en-US`. An option the browser rejects (a locale or time zone, a `RangeError`) writes one `console.error` and falls back to the browser default.
- **Enum keys.** `Badge<TEnum>`, `Lookup<TEnum>` and `Ordinal<TEnum>` key their maps by `JsonSerializer.Serialize(value, JsonSerializerOptions.Web)`: the text of a JSON string, the digits of a number, so the key equals `String(value)` of the row value in the browser. A converter attribute on the enum (`JsonStringEnumConverter`, `JsonStringEnumMemberName`) counts; a converter only in the app's serializer options does not (documented on the factories).
- **Output.** A preset whose result is text returns a string, so the CSV export and the copy of rows hold the formatted text (upstream uses a formatter for the export only when it returns a string); a preset returns an element only when it needs one. Intl formatter objects are created once per column: the cache key is `ctx.args`, one object per resolved column function. An element preset keeps its node per row object and column (`ctx.args`) while its value stays the same, so the node keeps its state across the grid's renders; a node that the current render already returned is not returned again in the same render (the grouped cell of a group row has the row object of its first data row), and new `Data` brings new row objects, which empties the cache.
- **Values.** `null`, `undefined` and `""` show `nullText` (empty by default). A `yyyy-MM-dd` string (`DateOnly`) is a calendar day and an `HH:mm[:ss[.f]]` string (`TimeOnly`) a time of day: both are formatted in UTC, so every time zone shows the same day; `timeZone` applies to instants only. `Duration` reads numbers, ISO 8601 durations and the `TimeSpan` JSON form. Map lookups read own keys only (`Object.hasOwn`), so a value such as `constructor` finds nothing.
- **DOM and URLs.** Presets build DOM with `createElement`, `setAttribute` and `textContent` only (no `innerHTML`, no HTML parsing; `PresetScriptContractTests` scans the package JavaScript). Each icon-only element gets an accessible name (`label` on `wa-icon`), and a badge always shows its text. A link URL comes from a C# template: each placeholder value is URL-encoded, a template whose literal parts name a scheme other than http, https, mailto or tel is rejected in C#, the browser checks the scheme of the built URL again and shows text for any other, and a link with an empty placeholder shows text. An image URL (`Image`, `Avatar`) may be relative, http or https only, in C# (`CellTemplate.ValidateImageUrl`) and in the browser; any other leaves the image out. A color swatch sets its color through `style.setProperty`, after `CSS.supports('color', value)`. The Blazor router intercepts a relative link in the grid's shadow root (`cell-presets.spec.js`).
- **Composite presets.** `WaDataGridFooters`, `Trend`, `DataBar` and `WaDataGridDetailField.Format` take a text preset of `WaDataGridFormatters` as `format`, written as `{ name, args }`; the preset function calls that text preset with its own arguments. A reference that is not a text preset that formats a value without its row (`PresetNames.TextFormats`: not `Template`) throws `ArgumentException`. The footer aggregates and the computed `DataBar` limits read the column of `ctx.column` from `grid.columns` (its `value` function, else its `field`) and leave out values that are not numbers; the `DataBar` limits come from `grid.data`, so in server mode only from the loaded page (set `min` and `max` there).
- **Class rules.** `WaDataGridClassRule(className, condition)` with an optional `Field`; the first rule that matches gives the class (a cell rule tests its cell value unless the rule names a field; a row rule needs a field). `WaDataGridCondition`: `EqualTo` and `In` compare `String(value)` with the key (a number key is its JSON form, an enum key as for `Badge<TEnum>`), `LessThan`, `GreaterThan` and `Between` (inclusive) compare numbers or, with a `DateOnly` or `DateTimeOffset` bound, dates (a `DateOnly` is UTC midnight on both sides), `IsNull`, `IsTrue`, `IsFalse`, and `Matches` (a JavaScript pattern; an invalid one writes one `console.error` and never matches). The equality condition is `EqualTo`, because a static `Equals` would hide `object.Equals`. Style the classes with `ShadowStyles`.
- **Search and filter options.** `WaDataGridSearch.Formatted(columns)` reads the labels (and the lookup fallback) of the searchable columns whose formatter is a lookup, badge, tag, tags or icon preset. The grid calls `searchFn(value, term, row)` once per row and searchable column without the column id, so the function matches the raw value (case-insensitive substring, as the built-in search) or a label of any of those columns of the row (cached per row and term). `WaDataGridFilterOptions` builds `FilterOptions` in C# from labels, an enum or such a formatter.
- **Interactive presets.** `Button`, `Actions` (each `WaDataGridAction` an icon button with its label as the accessible name, or a text button; `InMenu` actions in one `wa-dropdown`; `HiddenField`, `DisabledField`, `Tooltip` through `wa-tooltip` with an id in the shadow root), `Menu`, `Switch` and `Checkbox`. The controls are `wa-button` (Enter and Space reach it: the grid's `GridNavigationController` passes them to `button`, `wa-button` and `wa-checkbox`, and to the `checkbox` input inside `wa-switch`) and `wa-dropdown` (the grid ignores the keys of a `wa-dropdown`). Switch and checkbox raise their action on `change` with `{ checked }`: the element shows the new state at once, so the handler updates its row and pushes `Data` (data with the old state shows the old state again, design 9.5). Verified in Chromium with WA 3.14.0 (`cell-actions.spec.js`): Tab from a cell moves into the buttons of the next cell, and Enter and Space click a focused button (R4); a `wa-dropdown` in a pinned column and in the last row opens in the viewport, unclipped, and its item reaches the bridge (R6).
- **The ctx helpers.** `wwwroot\data-grid-context.js` is a context decorator (registered by the initializer with the presets) for the functions of a `wa-data-grid`, column and grid members alike: `ctx.emit(action, payload?, source?)` raises a cell action for the row of the call, `ctx.invoke(action, payload?, source?)` asks .NET (see "Requests to .NET" below) (`column` is empty for a grid member, `row` null for a footer; the optional element or event gives the row index, else -1), `ctx.h(tag, props, ...children)` builds DOM (a primitive prop is an attribute, `true` an empty one, an object a property, an `on*` function a listener; `action`/`payload` add the action click; text children are text nodes; a prop whose name contains `HTML`, `srcdoc`, an `on*` text and a URL prop with a scheme other than http, https, mailto or tel are refused with one `console.error`), `ctx.preset(name, options)` calls a cell preset for the value of the call, `ctx.format.<textPreset>(value, options)` formats a value without its row, and `ctx.cache(key, create)` keeps a node per row object, function and key (the node cache rules above; per function without a row). The options of `preset` and `format` are normalized once per function and option text (`culture` from the options, else `ctx.args.culture`, else the browser default), so the preset caches also work for a new object literal per call. Measured in Node 24 over 10,000 rows: the decorator adds no cost to a call that does not use the helpers (about 65 ns for the wrapper with or without it); `ctx.format.number` costs about 0.9 µs with stable options and about 1.9 µs with a new object literal.
- **Lit (risk R2).** A function may return a Lit 3 `TemplateResult` of the app's own copy of Lit (for example `lit@3.3.1` from a CDN, imported in a collocated module): verified with WA 3.14.0, the grid renders it, its `@click` bindings work and its declarative actions pair (`cell-actions.spec.js`, `/testing/lit-cells`). The library itself has no Lit dependency; `ctx.h` is the way without Lit. Recheck on each upgrade (the grid's own Lit version).
- **Cell actions.** Content that raises an action dispatches `wablazor-cell-action` on the grid host (`bubbles`, `composed`) with `{ column, action, rowKey, row, value, payload, rowIndex }`; `rowIndex` is the `data-row-index` of the cell. Three ways raise one (design 9.3): the presets, `ctx.emit`/`ctx.h({ action })`, and an element with `data-wablazor-action="id"` (optional `data-wablazor-action-payload` with JSON) in the output of any function, clicked or activated with Enter or Space on a focused button. The declarative action pairs with the `wa-cell-click` of its click, which gives the column, row, value and row index; a click with no `wa-cell-click` (a detail panel, a footer, a group row) drops the action with one `console.warn` (use `ctx.emit` there). The Extensions initializer registers the type with `registerCustomEventType` (`createEventArgs: cellActionArgs`, the row and payload sanitized to depth 4), and `[EventHandler("onwablazor-cell-action", ...)]` declares the Razor attribute, which `WaDataGrid` passes to its element through `AdditionalAttributes`. The Razor compiler reads `[EventHandler]` only from a public class named **`EventHandlers`** (the declaring class is `DataGrid\EventHandlers.cs`); on another class it passes `@onwablazor-cell-action="Handler"` on as a text attribute and the handler never runs. `CellActionEventTests` checks the declaration, the registration and the payload keys against `WaDataGridCellActionEventArgs`.
- **Decision D4.** A click that raises an action, hits a declarative action, or hits a control of a preset (a menu trigger or item, a switch, a checkbox, a copy button) does not reach Blazor as `wa-cell-click`. Per grid, the bridge (`ensureCellActionBridge`, installed when such content is created and by the ctx decorator) keeps the click in flight from a capture listener on the grid's shadow root; a `wa-cell-click` listener on the host stops the propagation of the `wa-cell-click` of a marked click, so Blazor, which listens on the document, never sees it, while listeners on the grid element do. The click ends when it reaches the host, or after one task. An action raised outside a click (a `change`, a menu selection by keyboard) marks nothing. The grid's keyboard navigation consumes Enter on cell content that is not a button or a form control (an `a` included), so a keyboard user cannot follow a `Link` with Enter (a Web Awesome behavior; recheck on each upgrade, `GridNavigationController` `TOGGLE_TAGS`).
- **Performance.** A virtualized grid of 10,000 rows with eight preset columns (number, currency, date, badge, progress bar, boolean icon, trend, data bar; `/testing/cell-actions?perf=true`) scrolled in Chromium for 6 s with 120 px per frame and four jumps: no long task, frame time p50 16.7 ms, p95 16.8 ms, the longest 34 ms (design 11.5).
- **Requests to .NET (design 9.6).** `ctx.invoke(action, payload?, source?)` (in `data-grid-context.js`, for every `wa-data-grid` member, cells, detail panels and footers alike) sends the payload of a cell action (`cellActionPayload`: column, action, row key, the sanitized row, value, payload, row index) to .NET and returns a Promise. The .NET side is the companion component `WaDataGridRequestHandler`, which wraps the grids: it renders one `div` with `display: contents` and, after its first render, registers a `DotNetObjectReference` of an internal receiver for that element (`registerRequestHandler` of `wwwroot\data-grid-requests.js`, imported by path). The browser keeps the references in a `WeakMap` on `globalThis[Symbol.for('WebAwesome.Blazor.Extensions.cellRequests')]` and finds the handler through the ancestors of the grid element at the time of the call, so a grid element that Blazor replaces (a new `@key`) and several grids use the same handler. Why a wrapper: Extensions adds no parameter to `WaDataGrid` (section 17); a companion bound with `@ref` would get the reference only after the page renders again, and a registration API returning `IAsyncDisposable` would need `OnAfterRenderAsync`, disposal code and a new registration for a replaced element in every page. The receiver's `[JSInvokable]` method (`CellRequestReceiver.InvokeMethodName`, `invokeMethodName` in the module) runs `OnRequest` (`Func<WaDataGridCellActionEventArgs, Task<object?>>`) and answers `{ value, error }`: the Promise resolves with the value, or rejects with an `Error` with the message of a `WaDataGridRequestException`; any other exception goes to the Blazor interop (on WebAssembly its text reaches the browser, on Blazor Server only with detailed errors), and the module rejects with an `Error` that names the action. A missing handler waits up to 2 s for a registration (it arrives after the first cells: the import and the registration are asynchronous, two round trips on Blazor Server), then rejects; so does a handler without `OnRequest`, a disposed reference and a lost connection. Each call is its own `invokeMethodAsync`, so concurrent calls get their own answers. `DisposeAsync` unregisters the element (a `JSDisconnectedException` is ignored: the circuit and its registration are gone), disposes the module reference and the `DotNetObjectReference`. A grid function is synchronous, so a cell shows a pending state, keeps the answer and calls `ctx.grid.requestUpdate()` when it arrives; key the answers by the row key, because `WaDataGrid` pushes `Data` on every parameter set (also when the handler renders the page), which gives new row objects; the footer and the detail panel are built again on each render too, so their answers live outside their nodes (`CellRequestsHarness.razor.js`).
- **Static Razor templates (design 10).** `WaDataGridRazorTemplates<TRow>`: `Add(key, RenderFragment<TRow>)`, `Formatter(key, params uses)` (`WaJsFunction.Registered("wab.dataGrid.razorTemplate")` with `{ key }`; the name `template` belongs to the text template preset) and `RenderAsync(IServiceProvider, rows)`. `RenderAsync` creates one `HtmlRenderer` from the page's service provider per call (the components of a template get the services of the page scope), renders each template for each row on the renderer's dispatcher through the internal `RazorTemplateHost`, and disposes the renderer: an `HtmlRenderer` keeps every root component it rendered until it is disposed, so a renderer from DI would grow with each data push on a long circuit. Each row becomes an internal `RazorTemplateRow` whose converter writes the row with the serializer options of the push (the interop options), then `$wabTemplateHtml` (key to HTML); no column reads it, so sort, filter, search, copy and the CSV export see the row; the payload of a cell action or a request leaves it out. The preset `razorTemplate` (`data-grid-presets.js`) reads the HTML of its key, parses each text once into a `<template>` (bounded cache, `data-grid-templates.js`: the only HTML parse of the package; the content of a `<template>` is inert, so no script runs and nothing upgrades during the parse), imports a copy into a `span` with `display: contents`, keeps it per row object and column (the node cache), and installs the action bridge, so `data-wablazor-action` in the HTML raises cell actions (D4 included). The HTML is static: `@onclick` and a wrapper that needs JS interop after its render do not work. Razor encodes text and attribute values; a `MarkupString` with user content is not safe. Cost: one render per template and row on each `RenderAsync`, on the server or in WebAssembly, and the HTML (JSON-escaped) in each row: for server mode and small pages. Elements in the HTML need `Uses` (the `uses` of `Formatter`), as for any function output in the shadow root. Verified on both hosts (`cell-requests.spec.js`).
- **Tests.** The descriptor of each factory, the rule JSON, enum keys and template rules in `WebAwesome.Blazor.Extensions.Tests\DataGrid`; the browser behavior in `tools\e2e\tests\cell-presets.spec.js` (the registry and the DOM, rules, footers, search and sort of the presets on the free CDN; the cells, the CSV export, the node cache, the ordinal sort, the action event, D4 and the keyboard with Pro assets, in a time zone west of UTC) and `tools\e2e\tests\cell-actions.spec.js` (the ctx helpers on the free CDN; the interactive presets, D4, R2, R4, R6, the ctx helpers and declarative actions in a cell, a detail panel and a footer, the rule presets and the demo example with Pro assets), `RequestHandlerTests`, `RequestScriptContractTests` and `RazorTemplateTests` (the request handler, the module contract, the template HTML and the row JSON), and `tools\e2e\tests\cell-requests.spec.js` (the .NET round trip, rejections, concurrency and the wait for a handler on the free CDN; `ctx.invoke` in a cell, a detail panel and a footer, a replaced grid element, and the Razor templates with Pro assets; run it on both hosts).

## Inspector metadata

The wrappers can write placement metadata for the WA Inspector browser extension (`tools\wa-inspector`; usage, the attribute table and the matching rules in `docs\inspector\README.md`). The Claude Code plugin `wablazor` (`tools\wablazor-marketplace`) has the skills `install-inspector` (installs the extension, which the published plugin bundles) and `wa-review-apply` (applies the exported change lists). The mechanism is `Infrastructure\WaInspectorMetadata.cs` (design `tasks\WA-3.14\WAB-62\plan.md`):

- **Opt-in, process-wide.** `WebAwesomeOptions.EmitInspectorMetadata` (configuration key `WebAwesome:EmitInspectorMetadata`) defaults to `false`. `AddWebAwesome` copies it to the static `WaInspectorMetadata.Enabled`, because a wrapper has no injected services to read options from. The setting belongs to the host's environment (development, test), not to a circuit. When it is off, a wrapper writes nothing and pays one flag check.
- **Attributes.** `data-wablazor-component` (the wrapper type name without the generic arity), `data-wablazor-chain` (the application component types from the render root, without `Microsoft.*` and `System.*` types), `data-wablazor-placement` (a hash of the full path) and `data-wablazor-site` (a hash of the last level). The names are the `Constants.Inspector*Attribute` constants.
- **Placement and site.** A level is the type of the rendering parent, the sequence numbers of the frames from the parent's root to the child's component frame in the parent's current render tree, and the child type. Razor emits sequence numbers as compile-time constants per source position, and a loop reuses them. So all instances of one loop share a placement, and the same markup at another position gets another one. The site is the last level only: the same source position wherever its parent component is used. The hashes are FNV-1a, 64 bits, shortened to 12 hex digits.
- **Reflection with fallback.** Blazor has no public API for the parent frames of a component. The path comes from `ComponentBase._renderHandle`, `RenderHandle._renderer`, `Renderer.GetComponentState` and `Renderer.GetCurrentRenderTreeFrames`, resolved once into delegates. If one member is missing (another .NET version, trimming) or a call fails, the wrapper writes `data-wablazor-component` only. Each instance computes its placement once, at its first render; the levels of the ancestors are cached in a `ConditionalWeakTable`. Recheck the members on each new .NET version.
- **Every wrapper root calls it.** `OpenWaElement` calls `WaInspectorMetadata.AddAttributes` right after the element opens, so a new wrapper gets the metadata through it. `WaLayoutBase.AddCommonLayoutAttributes` and the layout wrappers that open their own element (`WaFlank`, `WaSplit`, `WaGrid`, `WaFrame`, `WaText`, `WaVisuallyHidden`) call it themselves. A wrapper that opens its root element in another way must call it too.
- **Tests.** `WaInspectorMetadataTests` (in a non-parallel collection, because the switch is process-wide): off by default, the attributes when on, loop instances share a placement, two call sites differ, the same component at two positions has the same site and another placement, child content is placed through the wrapper that renders it, the placement is stable across renders, the chain hides framework types, a layout wrapper writes the metadata, and the configuration binding.

## Dependencies

All versions live in `src\Directory.Packages.props` (Central Package Management — see `CLAUDE.md`), with two opposing policies:

- **The library ships minimal floors.** NuGet dependency versions are minimums, so every package the library carries into the nupkg (currently `Microsoft.AspNetCore.Components.Web`, `Microsoft.Extensions.Configuration.Abstractions`) stays at the **base release of the target major** (`9.0.0`, `10.0.0`) — a higher floor would force consumers to upgrade their framework packages for no reason. Raise a floor only when the library genuinely needs a later API or fix, and document why at the version entry. A side effect worth keeping: the test suite then validates against the minimum versions consumers can actually resolve.
- **The test harness and tooling track latest stable.** Test-only and build-only packages (test SDK/framework, bUnit, mocking, analyzers, SourceLink, and framework packages referenced only by tests or the demo apps) are kept current — there is no consumer impact, and staying recent picks up runner fixes and security patches. Known-vulnerability warnings (NU1902) are fixed by lifting the affected package, never by suppressing the warning.

## Multi-targeting

The library targets `net9.0;net10.0` with **a single shared code path — no `#if` divergence in library code**. Multi-targeting exists for dependency hygiene (framework package references conditioned per TFM via Central Package Management), not API divergence; net10.0 (LTS) is the primary, fully tested target. `#if` conditional compilation requires a documented reason; the standing evaluation of why none is warranted is archived at `tasks\WA-3.0\WAB-7\net10-blazor-evaluation.md` and is re-evaluated per .NET release (async validation in .NET 11 is the known future interaction point).

**The one owner-approved exception: attributes typed as a union of value types.** `wa-input`'s `min`/`max` are `number | string` in the CEM (a number for `type="number"`, an ISO date, time or local date-time for the date and time types), which C# before 15 cannot type as one parameter. Until then `WaInput` exposes a raw `string?` `Min`/`Max` plus one strongly typed accessor per value type (`MinDecimal`, `MinLong`, `MinULong`, `MinDate`, `MinTime`, `MinDateTime`, and the same for `Max`), each converted culture-free into the native form; at most one per bound may be set (`OnParametersSet` throws `InvalidOperationException` naming them), and `additionalAttributeParameters` lets the render checks sample each accessor against its attribute. The whole set is wrapped in `#if NET11_0_OR_GREATER` / `#error Use a union type here` / `#else` ... `#endif`, so the net11.0 target cannot build until it is replaced by a C# 15 union type: a deliberate breaking change on net11.0, with the TFM divergence it brings accepted by the owner. Apply the same pattern, and the same guard, to any other attribute whose Web Awesome type is a number/date/time union.
