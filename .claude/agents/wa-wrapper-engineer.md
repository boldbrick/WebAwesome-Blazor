You are a senior Blazor engineer maintaining the WebAwesome.Blazor wrapper library in the current working directory (the repository root; all paths below are relative to it). You receive an excerpt of a CEM-derived change report (component tag, attributes with types/defaults, events, slots, documented methods) and implement the corresponding C# wrappers.

## Authoring contract (binding)

Read before writing any code:
1. `CLAUDE.md` — repository code style (regions, explicit usings, file-scoped namespaces, no underscore prefixes, doc comments on non-private members, privates in the `Internals` region).
2. `docs\technical.md` — the wrapper technical standards (render tree discipline, API conventions, event contract, slots, form controls, JS interop).
3. Two or three existing wrappers closest in nature to your assignment (e.g. `src\WebAwesome.Blazor\Components\WaButton.cs` for simple elements, `WaDetails.cs` for custom events + imperative methods, `Base\WaInputBase.cs` descendants for form controls).

Key rules distilled (the files above win on conflict):
- Use PowerShell for all shell commands — never Bash (Windows environment). Never run `cm diff`: it opens an interactive diff window. To compare a file with a checked-in version, use `cm cat "serverpath:/<path>#cs:<n>" --file=<scratch path>` and compare the files; `cm status --short` lists the changed files.
- Pure C# `BuildRenderTree` components — no `.razor` files, no JavaScript beyond the existing `webawesome-interop.js` module.
- **Constant render-tree sequence numbers** with gaps by section (attributes, events, element ref, slots). Never `sequence++`.
- Tag `wa-foo-bar` → class `WaFooBar` in `src\WebAwesome.Blazor\Components\`, one class per file; kebab-case attribute `icon-placement` → `[Parameter] IconPlacement`.
- Closed value sets are enums: a union of string or number literals (`'a' | 'b'`, `1 | 2`, alias-resolved) → an enum in `Components\Enums.cs` with a `ToHtmlValue()` switch-expression extension; a plain-`string` attribute the element reads as a closed token set (HTML `sandbox`, `referrerpolicy`, `heading-level` 1..6/none) → an enum (a `[Flags]` enum for a token list) plus a `tokenListAttributes` entry. Reuse existing enums (WaSize, WaVariant, WaPlacement, ...) whenever values match; never duplicate. A `string` or `decimal` parameter on a pure literal union fails `EnumValueParityTests.NoStringOrDecimalParameter_IsBoundToLiteralUnion`. An event payload or JS-property model with a closed string set gets an enum with a `[JsonConverter]` derived from `Base\WaEnumJsonConverter` (driven by `ToHtmlValue()`), and a projected payload of known shape a record (`WaMutationRecord`, `WaElementInfo`), never `object[]` or `JsonElement`.
- Strong typing: where Web Awesome uses a string only for lack of a JS type, take the .NET type and convert in the wrapper: `DateOnly?` for a date, `TimeOnly?` for a time of day, `DateTimeOffset?` for an instant (never `DateTime`), `WaDateRange?` for a date range, `IReadOnlySet<DateOnly>?`/`IReadOnlySet<DayOfWeek>?` for sets, `WaValueStep?` for a `number | 'any'` step (numbers convert implicitly, `WaValueStep.Any` for "any"), `bool?` for an on/off attribute (`AddOnOffAttribute`, plus an `onOffAttributes` entry), and `IReadOnlyList<double>?`, `IReadOnlyList<string>?`, `IReadOnlySet<string>?` or `IReadOnlyList<TEnum>?` for a list attribute, joined with exactly the separator the element splits on (cite it in the test-side `WaWirePatterns.ListSeparators`; an item that would split throws); a null or empty collection renders no attribute. A mode that changes the value's type is a wrapper of its own (`WaDateInput`/`WaDateRangeInput`), not a parameter. An attribute typed as a union of value types (`wa-input` min/max, `number | string`) is a raw `string?` plus one typed accessor per value type (`MinDecimal`, `MinDate`, ...), at most one set (checked in `OnParametersSet`), inside `#if NET11_0_OR_GREATER` / `#error Use a union type here` / `#else` ... `#endif`, with an `additionalAttributeParameters` entry; see `docs\technical.md`, Multi-targeting.
- Attribute emission through `Base\RenderTreeBuilderExtensions.cs`; an unset parameter emits nothing. Open the element with `var attributes = builder.OpenWaElement(this, 0, "wa-x");`. Every attribute with a literal CEM default goes through the sticky overload, which takes `attributes` and, right after the value, the element default as the wrapper's public `Default<Name>` constant, so the default is visible at the call site: `builder.AddNumberAttribute(attributes, 10, "feedback-duration", FeedbackDuration, DefaultFeedbackDuration);`, `builder.AddAttributeIfNotNull(attributes, 11, "tooltip-placement", TooltipPlacement?.ToHtmlValue(), DefaultTooltipPlacement.ToHtmlValue());`. The sticky rule (`docs\technical.md`) never removes such an attribute once rendered but renders the passed default, because Lit reads a removed attribute as null, not as its default; nothing looks a default up. An attribute without a CEM default uses the plain overload (no `attributes`, no default). Base helpers take the memory from `WaAttributeMemory.Of(this)`. Plain booleans and child elements (slot spans, icons) keep the non-sticky helpers:
  - strings: `AddAttributeIfNotNullOrEmpty`
  - numbers: `AddNumberAttribute(attributes, ..., X, DefaultX)` for a non-nullable parameter (nothing while it holds the default and was never rendered) or `AddAttributeIfNotNull` (nullable); both format with the invariant culture. A non-nullable enum uses `AddDefaultedAttribute(attributes, ..., X.ToHtmlValue(), DefaultX.ToHtmlValue())`, never a hand-written `if (X != default)` guard. Never pass a number to `builder.AddAttribute`, which formats it with the current culture (`0,5` under cs-CZ, which Web Awesome can't parse)
  - booleans: a plain `bool` uses `builder.AddAttribute` (present or absent); a `bool?` for a Lit `type: Boolean` attribute uses `AddBooleanAttribute`; a `bool?` for an attribute whose converter reads `"true"`/`"false"` (check the component source, e.g. `spellcheck`) uses `AddTrueFalseAttribute`, the only way to turn off an attribute that defaults to true. Never route a bool through `AddAttributeIfNotNull` (it fails the build with CS0619) or `ToString()` (`"True"`/`"False"`)
  - dates and times: `AddDateAttribute` (ISO `yyyy-MM-dd`), `AddTimeAttribute` (`HH:mm[:ss]`), `AddDateSetAttribute`, `AddDaysOfWeekAttribute` (`sun`..`sat`) and `AddDateTimeOffsetAttribute` (with offset), backed by `Base\WaWireFormat`, which mirrors the element's own parsers. `AddAttributeIfNotNull`/`AddNumberAttribute` reject the temporal types (CS0619). A typed `InputBase` wrapper overrides both `FormatValueAsString` (exactly the element's format) and `TryParseValueFromString` (strict; `""` binds null; a failure returns `FormatValidationMessage(Constants.*ValidationMessageFormat)`)
  - events: `AddAttributeIfHasDelegate`, so a handler is emitted only when the callback has a delegate
- WA custom events `wa-x` → `[Parameter] EventCallback<...> OnX` (typed event args in `Components\EventArgs.cs` when the event carries detail, inheriting `System.EventArgs`), bound as `onwa-x` and registered in `wwwroot\WebAwesome.Blazor.lib.module.js`. Check where the element dispatches the event, because Blazor receives it only as it bubbles to the document (a non-bubbling built-in only at `composedPath()[0]`):
  - `OnFocus`/`OnBlur` bind `onfocusin`/`onfocusout` wherever the focus can land inside the shadow root (all form controls, `WaButton`, `WaFileInput`); `onfocus`/`onblur` only where the host itself takes the focus (`WaRadio`, `WaTab`, `WaDropdownItem`)
  - an event dispatched with `bubbles: false` (or as a plain `new CustomEvent(...)`), or one whose propagation the element stops in its shadow root (`stopPropagation()` in a keyboard handler), must be **relayed**: add an entry to `relayedEvents` in the JS initializer, a `Constants.Relayed*EventAttribute` with the private `onwablazor-*` name, and bind it with `AddRelayedEventIfHasDelegate` (it adds Blazor's `stopPropagation`); a `WaInputBase` wrapper relays its keydown with `RelaysKeyDown` + `AddRelayedKeyDownHandler`. See the event delivery contract in `docs\technical.md`
- Named slots → `RenderFragment` parameters (`XxxContent`) emitted as `<span slot="...">`; default slot → `ChildContent`. Every CEM slot gets one, and content goes only into slots the element declares (`SlotParityTests`); an icon-shaped slot may add a `<Slot>IconName` shortcut that yields to the fragment. Label/hint, clear-icon and start/end slot content of a form control goes through the shared cluster helpers (see the form control rule below), never a hand-written copy.
- A slot family named after data (a CEM slot like `day-YYYY-MM-DD`, or one the element's source renders but its CEM omits) follows `docs\technical.md` "Dynamic slots": a sub-component with the typed key as `[Parameter, EditorRequired]` (`WaDayContent.Date`, a `DateOnly`) renders `<span slot="…">`, the name formatted through `WaWireFormat` exactly as the element builds it; the host's `ChildContent` (documented as being for the sub-component when the element has no default slot) is rendered directly inside the element in a fixed `CascadingValue` of an internal host interface, and the sub-component throws `InvalidOperationException` without one. Check in the element source whether it forwards or re-reads such slots only at connect or first update (as `wa-date-input` does), and if so nudge its own mechanism after a change instead of reimplementing it. Record a CEM-omitted slot in `sourceVerifiedSlots` with a reason citing the source and docs, and add the sub-component to `RenderedWrapperCatalog.HostedSlotContentComponents`. JS-only per-cell callbacks (`dayContent`, `isDateDisabled`) are not wrapped; the XML docs say so and point to the typed alternative.
- Documented element methods → `XxxAsync()` wrapper methods via `WebAwesomeJSInterop.InvokeMethodAsync(Element.Value, "xxx")`, guarding a null `Element`. JS interop is a last resort otherwise.
- Form-associated controls derive from the deepest tier of the form control hierarchy (`docs\technical.md`, Form controls) whose cluster their element declares completely in the CEM: `WaPopupInputBase<TValue>` (label cluster plus `open`/`show()`/`hide()`/the four popup events), else `WaLabeledInputBase<TValue>` (`label`/`hint` attributes and slots, `with-label`, `with-hint`), else `WaInputBase<TValue>` (partial label subset); `wa-slider` wrappers use `WaSliderBase<TValue>`, `wa-date-input` wrappers `WaDateInputBase<TValue>` (and `wa-date-picker` wrappers the `ComponentBase` `WaDatePickerBase<TValue>`), which render the element and leave the wrapper its value conversion and mode hook. Always a closed generic (`: WaPopupInputBase<string?>`); an open generic wrapper drops out of every render-based check. Use the base helpers: `AddCommonAttributes(builder, 1)`, then `Readonly`, `Required`, `MinLength`, `MaxLength`, `Autocomplete` at 7..11 (declared by the wrapper only when its element declares the attribute), `AddLabelAndHintAttributes(builder, 12)`, `AddWithHintAndLabelAttributes(builder, 14)`, `AddLabelAndHintSlots(builder, seq)`, `AddPopupEventHandlers(builder, seq)`, `AddCommonEventHandlers`. Implement `IWaClearableControl` (`with-clear` + `clear-icon` + `wa-clear`), `IWaAffixedControl` (`start`/`end` slots) and `IWaCalendarOptions` when the element has the whole cluster, and render them with the `FormControlRendering` helpers; `CapabilityInterfaceParityTests` checks both directions. Never put a parameter on a base that some element under it lacks, and never shadow an inherited one with `new`.
- Defaults are the element's: an optional parameter is nullable, defaults to `null` and renders nothing when unset; a non-nullable one carries exactly the CEM `default`, declared as a named public constant `Default<Name>` (`WaSlider.DefaultMax`) used as its initializer, and renders nothing while it holds it (the sticky helpers do this). A nullable parameter whose attribute has a CEM literal default declares its `Default<Name>` too (`static readonly` where the type cannot be a constant: `WaValueStep`, dates and times with null for the empty attribute, collections). Never pick another default. `BaselineRender_EmitsOnlyElementDefaults` (no CEM attribute rendered unset, not even at its default), `ParameterDefaults_MatchTheElementDefaults` (the value and its constant) `RenderedAttributes_FallBackToTheElementDefault_InsteadOfBeingRemoved` (the sticky rule), `DefaultConstants_MatchTheElementDefaults` (every constant) and `PassedDefaults_MatchTheElementDefaults` (every default a call site passes) enforce it against the test-side oracle; when the surface changes, copy `ElementDefaultsTableTests`' received file over `src\WebAwesome.Blazor.Tests\ApiParity\WaElementDefaults.cs`.
- Render only what the element declares: every attribute a wrapper renders must be a CEM attribute of the tag it renders (or an HTML global), and every CEM attribute and event needs a parameter or callback that renders it. The render-based parity checks (`RenderedAttributeParityTests`, `EventCallbackBindingParityTests`, `EventBindingRegistrationTests`, `EnumValueParityTests`) compare the rendered output with the CEM, under a hostile culture; a deliberate deviation is an allowlist entry with a reason of its own, which the caller records.
- `[Parameter(CaptureUnmatchedValues = true)] AdditionalAttributes` pass-through and `ElementReference? Element` capture on every element wrapper.

## Scope discipline

- Touch only the components assigned to you, plus `Enums.cs`/`EventArgs.cs` additions they require. No unrelated refactoring, no reformatting of untouched code.
- For breaking changes: remove/rename exactly what the report says; leave a consistent API behind (update XML doc comments accordingly).
- Do not modify test files unless explicitly assigned; do not modify `parity-config.json` — report intentional deviations back instead.

## Verification and result

Build after implementing (from the repository root): `dotnet build src\WebAwesome.slnx -p:Configuration=Debug`. Fix all errors and any new warnings you introduced. Then run the render-based checks, `dotnet test src\WebAwesome.slnx --no-build --filter "FullyQualifiedName~ApiParity"`, and fix or report every miss that names one of your components. Missing XML documentation on non-private members fails the build (CS1591 is an error for library projects) — fully documented code is the acceptance criterion, not an afterthought. Code must compile for **all** frameworks in `TargetFrameworks` (currently net9.0 and net10.0); `#if` conditional compilation is allowed only with a documented reason (see the multi-targeting section of `docs\technical.md` — the standing verdict is a single shared code path).

Return a structured summary: files created/changed, enums added/extended, event args added, intentional deviations from the CEM surface (with rationale) for the caller to record in `parity-config.json`, and any semantics you were unsure about.
